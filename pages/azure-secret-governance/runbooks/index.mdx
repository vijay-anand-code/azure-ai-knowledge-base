# Runbooks

Seven runbooks in total. Four run on a fixed weekly schedule through the Azure Automation
Account. One runs manually, from a laptop, deliberately outside the Automation Account. Two are
one-time cleanup tools, used when resetting the SharePoint lists back to empty.

| Runbook | Where it runs | Schedule |
|---------|--------------|----------|
| `runbook_discovery.py` | Azure Automation | Weekly, `00:00` |
| `owner_sync_local.py` | A laptop, under the operator's own signed in session | Manual, run whenever `DevSecOpsOwnership` has changed |
| `runbook_owner_sync.py` | Azure Automation | Not scheduled by default, ticket-based alternative to the local script |
| `runbook_monitoring.py` | Azure Automation | Weekly, `00:30` |
| `runbook_rotation.py` | Azure Automation | Weekly, `01:00` |
| `runbook_cleanup_sharepoint.py` | Azure Automation, run manually | One time. Wipes `SecretAlertRegistry` and its backup |
| `runbook_cleanup_sharepoint_ignored.py` | Azure Automation, run manually | One time. Wipes `IgnoredSecretRegistry` and its backup |
| `runbook_cleanup_sharepoint_all.py` | Azure Automation, run manually | One time. Wipes all four lists in a single run |

## Secret severity buckets

Every runbook classifies secrets the same way, using days remaining until expiry:

| Bucket | Days remaining | What happens |
|--------|----------------|-------------|
| **P1**, tagged half | 0 to 3 | Jira ticket, Teams alert tagging a specific person, eligible for rotation |
| **P1**, plain half | 4 to 7 | Jira ticket, Teams alert with no tagging, eligible for rotation |
| **P2** | 8 to 30 | Jira ticket, Teams alert, eligible for rotation |
| **P3** | 31 to 60 | Jira ticket only, no Teams alert, eligible for rotation |
| **P4** | 61+ | Written to `SecretAlertRegistry` with owners stamped. No alert, no ticket, not rotated |
| **ExpiredManualReview** | expired 1 to 7 days ago | Jira ticket and Teams alert. Never auto rotated, a human has to check it manually |
| **Ignore** | expired 8+ days ago | Subject to the abandonment check below, not simply skipped |

<Callout type="info">
  0 to 3 days and 4 to 7 days are both bucket P1, not two separate buckets, this replaced an
  older five-bucket scheme where they were split into P1 and P2. Every bucket name below that
  point shifted down by one: old P3 is now P2, old P4 is now P3, old P5 (safe) is now P4.
</Callout>

<Callout type="warning">
  P1, P2, and P3 all raise a Jira ticket. An earlier version of this system left the tagged and
  untagged halves of what is now P1 out of ticket creation, so a secret with only a few days
  remaining could send a correctly worded critical Teams alert with no ticket behind it. That has
  been fixed. Every bucket except P4 (safe) reliably gets a ticket now.
</Callout>

## runbook_discovery.py

Scans every configured Entra ID tenant, classifies every secret, and writes the results to
SharePoint. This is the only runbook that ever creates a new row for a secret.

### What it does, step by step

1. Fetches every App Registration and its secrets, across every tenant listed in
   `CROSS-TENANT-TENANT-IDS`
2. Fetches owners for each app in parallel, twenty at a time
3. Reads the current state of both `SecretAlertRegistry` and `IgnoredSecretRegistry`
4. Writes a fresh backup of both lists, then deletes the previous run's backup rows. The new
   backup is always written before the old one is removed, so there is never a moment with zero
   backup if the run fails partway through
5. Classifies every secret into a bucket
6. Writes P1 through P4 into `SecretAlertRegistry`, and expired-8-plus-days secrets into
   `IgnoredSecretRegistry`
7. If a secret sitting in `IgnoredSecretRegistry` has a later expiry date now, meaning it was
   renewed in Entra, its row is moved back into `SecretAlertRegistry` automatically
8. Prints a reconciliation summary: total apps, total secrets, and how many landed in each list,
   meant to be checked against a manual count from the Entra command line

<Callout type="info">
  `DevSecOpsOwnership` (renamed from `ManualAppOwners`) is the one column this runbook never
  writes to, on either a new row or an existing one. Whatever a person has typed into that column
  stays exactly as they left it.
</Callout>

### Required Key Vault secrets

`GRAPH-TENANT-ID`, `HOME-TENANT-ID`, `SHAREPOINT-SITE-ID`, `SHAREPOINT-LIST-ID`,
`SHAREPOINT-BACKUP-LIST-ID`, `SHAREPOINT-IGNORED-LIST-ID`, `SHAREPOINT-IGNORED-BACKUP-LIST-ID`,
`CROSS-TENANT-APP-ID`, `CROSS-TENANT-TENANT-IDS`

## owner_sync_local.py

Reads `DevSecOpsOwnership` and adds the named identity as an Entra owner on the matching App
Registration. This runbook does not run on the Automation Account at all. It is a plain Python
script, run from a laptop, under the operator's own signed in session.

### Why this runs locally instead of on a schedule

Adding a new owner to an App Registration needs a broader Graph permission than anything else
in this system holds, and granting that permission to the shared automation identity would mean
every runbook sharing it could add ownership to any app in either tenant, unattended, with no
one specifically accountable for it. Running this step locally means the actual Entra write
happens under a real person's own sign in, with whatever role and approval requirements already
apply to that person, rather than under a shared identity with no single owner.

### How to run it

```bash
az login
```

```powershell
$env:ROTATOR_KV_URL = "<YOUR_KEY_VAULT_URL>"
python owner_sync_local.py
```

The script checks which tenant the current session is signed into, and processes apps in that
tenant first. If it finds an app belonging to a different configured tenant, it pauses and
prints the exact command to switch:

```
az login --tenant <tenant-id>
```

Run that in a second terminal, then return to the first and press Enter to continue.

<Callout type="warning">
  If a name typed into `DevSecOpsOwnership` matches more than one object in a tenant, for example
  two service principals with the same display name, the script adds all of them as owners and
  logs it clearly as ambiguous. It does not file a ticket or otherwise gate this. Check the
  summary output after every run for an ambiguous match, since this is the one place a typo or a
  genuine name collision could grant ownership to something unintended.
</Callout>

## runbook_owner_sync.py

An alternative to the local script, meant for environments where running a script from a
laptop is not workable. Instead of writing to Entra directly, it detects the gap between
`DevSecOpsOwnership` and Entra's actual owner list, and files a Jira ticket per gap containing the
exact command a person with the right role needs to run. It holds no write permission to Entra
at all, by design, so it cannot make the change itself under any circumstance.

Not scheduled by default. Enable it only if the local script genuinely does not fit your
environment.

## runbook_monitoring.py

Triggers the monitoring cycle. This runbook itself is a thin wrapper. It calls the container's
`/run` endpoint and returns as soon as the request is accepted, since the actual work happens in
the background and can take several minutes across a large tenant.

### What the monitoring cycle actually does

1. Fetches every App Registration's secrets, across every configured tenant, and reads
   `SecretAlertRegistry`
2. Backs up both `SecretAlertRegistry` and `IgnoredSecretRegistry`, archiving whatever was
   previously in each backup list to Storage as CSV first, then writing a fresh snapshot, then
   deleting the old backup rows. This runs before anything else touches either list. If backup
   fails, the whole run aborts without touching anything further. See the
   [SharePoint Setup](/azure-secret-governance/sharepoint) page for the exact ordering
3. For any row with `ProductName` filled in, looks up a Key Vault secret named exactly after
   that product and writes its value into `DevSecOpsOwnership` for that row, always overwriting
   whatever was there. A `ProductName` with no matching secret just leaves the row as-is
4. For any secret that's new to SharePoint and matches an existing row's `NewSecretKeyId` (meaning
   it's the freshly-rotated replacement for that row), copies `TeamName`, `ProductName`, and
   `ProductTeamsKeyVaultName` from that parent row automatically, see "Lineage tracking" on the
   `decision_engine.py` source page. **Note:** the current code actually writes this last field
   under the misspelled column name `ProductTeamkeyVaultName` (missing the "s"), a real bug; see
   the warning on the [SharePoint Setup](/azure-secret-governance/sharepoint) page
5. For any app where `DevSecOpsOwnership` is filled in on at least one row (directly, from the
   `ProductName` lookup, or from a lineage copy above), copies that value onto every other row
   belonging to the same app that does not have it yet
6. Re-stamps `AppOwners`, `TenantID`, and `ObjectID` from live Entra data on every row it touches,
   not just at first discovery
7. For P1, P2, and P3, and for ExpiredManualReview, raises a Jira ticket if one does not already
   exist, this fires on severity/bucket alone now, regardless of whether `DevSecOpsOwnership` is
   set. An app with no ownership set still gets tickets and alerts; ownership no longer gates
   ticket/alert creation, only whether monitoring keeps actively working the row afterward (see
   the note below)
8. For P1 and P2, also sends a Teams alert. Within P1, the 0 to 3 day half tags a specific
   person, read from `TEAMS-TAG-EMAIL` in Key Vault, the 4 to 7 day half does not
9. For secrets that have crossed 8 days expired, checks whether there is still a live Jira
   ticket before deciding what to do. See the abandonment check below
10. Updates SharePoint with the current bucket, notice text, and last checked date for every
    secret it processed

<Callout type="warning">
  An earlier version of this system gated ticket and Teams alert creation on `DevSecOpsOwnership`
  (then `ManualAppOwners`) being set, and step 6 above used to read "filters to only secrets whose
  app has ownership set, everything else is skipped." That gate has been removed, per an explicit
  client requirement: severity alone now decides whether a ticket or Teams alert gets raised, for
  both brand-new and existing rows. `DevSecOpsOwnership` being blank no longer blocks self-heal,
  escalation, or first-time ticket creation in monitoring; it's tracked only as an informational
  count. Rotation is a separate story: it still will not touch a secret whose app has no
  `DevSecOpsOwnership` set.
</Callout>

### The 8 day abandonment check

A secret this old is not moved out of the active list purely because of the day count. That
would risk hiding a secret someone is actively rotating right now. The actual decision:

- No Jira ticket at all, or the ticket is Canceled: genuinely abandoned, moved to
  `IgnoredSecretRegistry`
- Ticket is Done or Resolved, but the row was never marked Rotated: flagged as a possible sync
  gap between Jira and SharePoint, left visible for a person to check
- Ticket is In Progress, To Do, Blocked, or Awaiting Reporter: someone is actively engaged, so
  the row stays visible in `SecretAlertRegistry`, `AlertStatus` set to `OverdueManualReview`

### Required Key Vault secrets

`GRAPH-TENANT-ID`, `HOME-TENANT-ID`, `SHAREPOINT-SITE-ID`, `SHAREPOINT-LIST-ID`,
`SHAREPOINT-IGNORED-LIST-ID`, `SHAREPOINT-BACKUP-LIST-ID`, `SHAREPOINT-IGNORED-BACKUP-LIST-ID`,
`CROSS-TENANT-APP-ID`, `CROSS-TENANT-TENANT-IDS`, `JIRA-BASE-URL`,
`JIRA-API-TOKEN`, `JIRA-USER-EMAIL`, `JIRA-PROJECT-KEY`, `JIRA-ISSUE-TYPE`,
`TEAMS-WEBHOOK-URL`, `TEAMS-TAG-EMAIL`, `BACKUP-STORAGE-ACCOUNT-URL` (optional, archival only)

<Callout type="warning">
  `OWNER-EMAILS` and the older singular `OWNER-EMAIL` are not used to decide which secrets get
  monitored anymore, and neither is `DevSecOpsOwnership` (renamed from `ManualAppOwners`);
  tickets and Teams alerts now fire on bucket/severity alone. If a secret is not getting alerts or
  tickets and you expect it to, ownership is not the first thing to check anymore; look at its
  bucket and whether a Jira ticket already exists instead. `DevSecOpsOwnership` still matters for
  rotation, see below.
</Callout>

## runbook_rotation.py

Rotates secrets automatically for P1 through P3 apps, once `DevSecOpsOwnership` is set. P4 (61+
days, safe) is never rotation eligible.

### What it does, step by step

1. Reads `SecretAlertRegistry`, filtered to rows in an actionable status
2. Checks any row already marked `RotatedPendingDeployment`. If its Jira ticket is now closed,
   marks the row `Rotated`
3. Filters remaining candidates to only apps where `DevSecOpsOwnership` is set. Unlike
   monitoring's ticket/alert creation, which now fires on severity alone regardless of ownership,
   rotation still will not touch a secret until its app's ownership is set
4. For each remaining candidate in P1 through P3 within the rotation threshold, calls
   `addPassword` on the App Registration, using the credential for whichever tenant that app
   actually lives in
5. Reuses the row's `NewSecretVaultName` as the Key Vault secret name if one is already set (so it
   lands as a new version of the same entry), otherwise generates one from
   `ProductName-TeamName-AppName` and writes it back for future rotations to reuse
6. Stores the new secret value in the rotation Key Vault, unless the row's
   `ProductTeamsKeyVaultName` is filled in, in which case the value goes into that specifically
   named vault instead (the URL is derived by appending the standard Key Vault suffix)
7. Adds a Jira comment with the new key ID, expiry date, and Key Vault reference
8. Marks the row `RotatedPendingDeployment`, waiting for a person to deploy the new value and
   close the ticket

<Callout type="info">
  How long a newly rotated secret stays valid for is controlled by `SECRET-VALIDITY-DAYS` in Key
  Vault. Change that number and every secret rotated afterward picks up the new value, no code
  change needed. It falls back to 365 days if not set.
</Callout>

### Required Key Vault secrets

`GRAPH-TENANT-ID`, `HOME-TENANT-ID`, `SHAREPOINT-SITE-ID`, `SHAREPOINT-LIST-ID`,
`CROSS-TENANT-APP-ID`, `CROSS-TENANT-TENANT-IDS`, `SECRET-VALIDITY-DAYS`, `JIRA-BASE-URL`,
`JIRA-API-TOKEN`, `JIRA-USER-EMAIL`

## Cleanup runbooks

Three separate scripts, each a full, permanent reset of the lists it touches. None of them are
meant to run on a schedule. Run one of them only when you deliberately want to wipe data and
start fresh, most often before a clean test of the discovery and backup cycle.

| Script | Wipes |
|--------|-------|
| `runbook_cleanup_sharepoint.py` | `SecretAlertRegistry`, `SecretAlertRegistryBackup` |
| `runbook_cleanup_sharepoint_ignored.py` | `IgnoredSecretRegistry`, `IgnoredSecretRegistryBackup` |
| `runbook_cleanup_sharepoint_all.py` | All four lists in one run |

<Callout type="warning">
  These delete every row permanently, including the entire backup snapshot. Run discovery again
  immediately afterward, since there is nothing to restore from until it completes and writes a
  fresh backup of its own.
</Callout>

## Setting up the Automation Account

<Steps>

### Create Automation Variables

In the Azure Automation Account, go to Shared Resources, Variables, and create:

| Name | Value |
|------|-------|
| `ROTATOR_KV_URL` | URL of the config Key Vault |
| `ROTATION_KV_URL` | URL of the rotation Key Vault |
| `UAMI_CLIENT_ID` | Client ID of the User-Assigned Managed Identity |
| `AGENT_ENDPOINT` | `https://<YOUR_CONTAINER_APP_FQDN>/run` |
| `AGENT_API_KEY` | Leave blank to disable, or set a shared key value |

### Assign the managed identity to the Automation Account

```bash
az automation account identity assign \
  --automation-account-name <YOUR_AUTOMATION_ACCOUNT> \
  --resource-group <YOUR_RG> \
  --identity-type UserAssigned \
  --user-assigned <UAMI_RESOURCE_ID>
```

### Grant the identity access to both Key Vaults

```bash
az keyvault set-policy \
  --name <YOUR_CONFIG_KEY_VAULT> \
  --object-id <UAMI_PRINCIPAL_ID> \
  --secret-permissions get list

az keyvault set-policy \
  --name <YOUR_ROTATION_KEY_VAULT> \
  --object-id <UAMI_PRINCIPAL_ID> \
  --secret-permissions get list set
```

### Import each runbook

For each `.py` file, in the Automation Account, go to Process Automation, Runbooks, Create a
runbook.

- Name it after the file
- Runtime: Python 3.10
- Paste in the script content
- Publish

### Add schedules

Create three schedules under Shared Resources, Schedules, then link each one to its runbook
under the runbook's own Schedules tab:

| Schedule | Time | Recurrence | Linked to |
|----------|------|-----------|-----------|
| Weekly Discovery | `00:00` | Every 7 days | `runbook_discovery.py` |
| Weekly Monitoring | `00:30` | Every 7 days | `runbook_monitoring.py` |
| Weekly Rotation | `01:00` | Every 7 days | `runbook_rotation.py` |

<Callout type="info">
  `owner_sync_local.py` is never scheduled, since it needs a person present to run it. Do not
  create a schedule for it.
</Callout>

</Steps>

## Troubleshooting

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| A secret never gets a ticket or alert | The secret is in bucket P4 (safe), the only bucket that never gets one, or it's an unrecognized/unparseable expiry date | Check `ExpiryBucket` on the row. Tickets and Teams alerts fire on severity alone now, not on `DevSecOpsOwnership` |
| A secret gets tickets/alerts but rotation never touches it | `DevSecOpsOwnership` is blank for that app | Fill it in on any one row for the app (directly, or via `ProductName`), monitoring propagates it to the rest automatically on the next run, and rotation only acts once it's set |
| Discovery reconciliation totals do not match | A write failed partway through | Check the run's error list, the summary always prints total apps and secrets seen, separate from what actually got written |
| Backup rows look wrong or missing | Check whether the backup was written before or after the purge | The backup step always writes this run's snapshot first, then deletes the previous run's rows. A number that looks low is usually the previous run's smaller starting count, not a bug |
| A Jira status change does not reach SharePoint | The automation rule's trigger list is missing that status | See the Jira automation page: the live KAN project workflow has four real statuses (To Do, In Progress, Waiting for Customer, Resolved), the trigger needs to watch all four |
| Rotation skips a secret that looks eligible | `DevSecOpsOwnership` is blank, or the secret's bucket is P4 | P4 (61+ days, safe) is never rotation eligible by design. Everything else needs `DevSecOpsOwnership` set |
| Secrets from only one tenant show up | `CROSS-TENANT-TENANT-IDS` is missing a tenant, or still set to the old singular `CROSS-TENANT-TENANT-ID` with only one value | Set the plural secret with every tenant ID, comma separated |
