# Runbooks

Three Python runbooks run inside Azure Automation Account on a weekly schedule.
Two additional utility runbooks are available for setup and maintenance.

---

## Weekly schedule

```
Monday 00:00 — runbook_discovery    (scans all apps, stamps owners to SharePoint)
Monday 00:30 — runbook_monitoring   (triggers monitoring container)
Monday 01:00 — runbook_rotation     (rotates expiring secrets)
```

The 30-minute gaps are intentional — discovery must finish stamping `AppOwners` before
monitoring reads them, and monitoring must finish creating Jira tickets before rotation
needs to check them.

---

## Authentication — Federated Credential

All three runbooks authenticate to Microsoft Graph using a **federated credential** flow —
no client secrets or certificates needed anywhere.

```
UAMI (Managed Identity)
  ↓ gets assertion token (api://AzureADTokenExchange)
App Registration (azure-secretgovernance-cross-tenant)
  ↓ exchanges assertion for Graph API token
Microsoft Graph API
  ↓ grants access based on App Registration permissions
Entra ID / SharePoint / Jira / Teams
```

### Required App Registration permissions

The App Registration must have these Graph permissions with admin consent granted:

| Permission | Type | Purpose |
|-----------|------|---------|
| `Application.ReadWrite.OwnedBy` | Application | Read all App Registrations, write secrets only on owned apps |
| `Sites.Selected` | Application | Read/write the SecretAlertRegistry SharePoint list only |

### Required Key Vault secrets (all runbooks)

| Secret | Purpose |
|--------|---------|
| `GRAPH-TENANT-ID` | Azure tenant ID |
| `SHAREPOINT-SITE-ID` | SharePoint site composite ID (3-part format) |
| `SHAREPOINT-LIST-ID` | SecretAlertRegistry list ID |
| `CROSS-TENANT-APP-ID` | App Registration client ID |
| `CROSS-TENANT-TENANT-ID` | Tenant ID where App Registration lives |

### Required Automation Variables (all runbooks)

| Variable | Value |
|----------|-------|
| `ROTATOR_KV_URL` | Config Key Vault URL |
| `UAMI_CLIENT_ID` | User-Assigned Managed Identity client ID |

<Callout type="info">
  The `SHAREPOINT-SITE-ID` must be the full three-part composite ID returned by Graph API —
  not the Web ID from SharePoint site settings. Get it by running:

  ```
  GET https://graph.microsoft.com/v1.0/sites/<tenant>.sharepoint.com:/sites/<site-name>
  ```

  Copy the `id` field from the response — it looks like:
  `contoso.sharepoint.com,abc123...,def456...`
</Callout>

## runbook_discovery.py

**Purpose:** Scans ALL App Registrations from Entra ID, fetches their owners in parallel,
classifies every secret by severity level, and batch-writes rows to SharePoint.

**Runs:** Weekly at 00:00. Also run manually when new App Registrations are added.

### What it does

- Fetches all App Registrations via `GET /v1.0/applications` — all apps, all secrets
- Fetches owners for every app in parallel using `ThreadPoolExecutor` (20 workers)
- Classifies each secret into P1 / P2 / P3 / P4 / ExpiredManualReview / Ignore
- Batch-writes to SharePoint using Graph `$batch` — up to 20 writes per HTTP call
- New secrets → creates row with `AlertStatus = Discovered`
- Existing rows → updates `AppOwners`, `ExpiryBucket` (SeverityLevel), `ExpirationDate` only
  (never overwrites `AlertStatus` — monitoring manages that)

### Key behaviours

| Behaviour | Detail |
|-----------|--------|
| **All secrets included** | P4 secrets (61+ days) are written to SharePoint so owners are stamped before they age into P3 |
| **Ignore bucket skipped** | Secrets expired 8+ days ago are not written — no value in tracking them |
| **AlertStatus never overwritten** | Updates to existing rows never touch `AlertStatus` — only monitoring changes it |
| **404 retry** | If a PATCH returns 404 (stale item ID), automatically retries as a POST |
| **Transient error retry** | Each SharePoint write retries up to 3 times with exponential backoff |
| **Parallel owner fetching** | 255 apps × ~50ms per owner call = sequential takes 13s. Parallel drops it to under 1s |

## runbook_monitoring.py

**Purpose:** Triggers the monitoring container (`/run` endpoint on Container 1).
The container does the actual work — this runbook just fires the request and returns.

**Runs:** Weekly at 00:30, 30 minutes after discovery.

### What it does

Sends a POST to the Container App `/run` endpoint with an instruction to run the
weekly monitoring check. The container runs the full monitoring cycle in the background
and the runbook returns immediately — avoiding timeout issues.

### Automation Variables required

| Variable | Value |
|----------|-------|
| `AGENT_ENDPOINT` | `https://<fqdn>/run` |
| `AGENT_API_KEY` | Shared secret header value (set to empty string `""` to disable) |

<Callout type="info">
  To bypass LangChain and call monitoring directly — avoiding GPT-4o rate limits —
  change `AGENT_ENDPOINT` to `https://<fqdn>/run-monitoring`. This calls Container 2
  directly with zero OpenAI tokens used.
</Callout>

### Expected output

```
[OK] Monitoring cycle triggered successfully.
  Started at : 2026-07-17T00:30:00Z
  Message    : Cycle triggered — agent running in background
  Summary    : Agent running in background — check container logs
```

## runbook_rotation.py

**Purpose:** Rotates expiring secrets for owned App Registrations, stores new values
in Key Vault, adds Jira comments, and updates SharePoint.

**Runs:** Weekly at 01:00, 1 hour after monitoring.

### What it does in two phases

**Phase A — Closure check**

Reads all `RotatedPendingDeployment` rows and checks if their Jira ticket is closed.
If closed → updates SharePoint to `Rotated`. If still open → updates `LastChecked` only.

**Phase B — Proactive rotation**

For each actionable row (P1/P2/P3) owned by the configured owner:

- Checks the Jira ticket is still open (skips if closed — someone already handled it)
- Calls `POST /applications/{id}/addPassword` to create a new secret in Entra
- Stores the new secret value in the rotation Key Vault
- Adds a comment to the Jira ticket with the new keyId, expiry, and Key Vault name
- Updates SharePoint to `RotatedPendingDeployment`
- Waits 5 seconds before the next rotation (prevents Azure AD concurrency conflicts)

### Ownership filter

Only secrets where `AppOwners` contains a value from the `OWNER-EMAILS` Key Vault secret
are rotated. Apps where the App Registration is not listed as an Entra owner will return
403 from Graph — providing a second layer of protection at the API level.

### Key behaviours

| Behaviour | Detail |
|-----------|--------|
| **Never double-rotates** | If `NewSecretVaultName` is already set on a row, it is skipped |
| **Jira check before rotation** | If the Jira ticket is already closed, marks as `JiraClosed-Unverified` instead of rotating |
| **5s pause between rotations** | Prevents Azure AD concurrency conflicts on `addPassword` |
| **OwnedBy enforced by API** | Non-owned apps return 403 — the system cannot accidentally rotate them |

### Additional Key Vault secrets required

| Secret | Purpose |
|--------|---------|
| `JIRA-BASE-URL` | Jira instance URL |
| `JIRA-API-TOKEN` | Jira API token |
| `JIRA-USER-EMAIL` | Jira account email |
| `OWNER-EMAILS` | Comma-separated App Registration display name — e.g. `azure-secretgovernance-cross-tenant` |

### Additional Automation Variables required

| Variable | Value |
|----------|-------|
| `ROTATION_KV_URL` | Rotation Key Vault URL (where new secrets are stored) |

<Callout type="warning">
  `OWNER-EMAILS` must match the `AppOwners` value stamped in SharePoint by the discovery
  runbook. If the App Registration is not listed as an Entra owner on the App Registration,
  rotation will be skipped — this is enforced at the Graph API level (HTTP 403).
</Callout>

## runbook_cleanup_sharepoint.py

**Purpose:** Utility runbook — deletes ALL rows from `SecretAlertRegistry`. Use this
to reset the list before a fresh test run.

**Runs:** Manually only — never scheduled.

<Callout type="warning">
  This permanently deletes all rows. Run `runbook_discovery` immediately after to
  repopulate. Only use on test environments or when intentionally starting fresh.
</Callout>

### What it does

Fetches all item IDs from SharePoint (with pagination) and deletes each one with a
100ms pause between deletions to avoid throttling. Prints progress every 50 deletions.

```
Azure Portal → Automation Account → Runbooks
→ runbook_cleanup_sharepoint → Start

Expected output:
  Total rows found : 1499
  Deleted          : 1499
  Failed           : 0
  ✓ Done — run discovery runbook next to repopulate.
```

## How to upload runbooks to Azure Automation

<Steps>

### Go to your Automation Account

```
Azure Portal → Automation Accounts → <your-account> → Runbooks
```

### Import each runbook

Click **Import a runbook** for each file:

| File | Runtime |
|------|---------|
| `runbook_discovery.py` | Python 3.10 |
| `runbook_monitoring.py` | Python 3.10 |
| `runbook_rotation.py` | Python 3.10 |
| `runbook_cleanup_sharepoint.py` | Python 3.10 |

### Publish after import

After importing each runbook, click **Publish** — runbooks stay in Draft state until published.

### Set Automation Variables

```
Automation Account → Variables → + Add a variable
```

Add all variables listed in the sections above.

### Schedule the runbooks

```
Automation Account → Schedules → + Add a schedule
```

| Runbook | Schedule | Time |
|---------|----------|------|
| `runbook_discovery` | Weekly | Monday 00:00 UTC |
| `runbook_monitoring` | Weekly | Monday 00:30 UTC |
| `runbook_rotation` | Weekly | Monday 01:00 UTC |

</Steps>

## Troubleshooting

| Error | Cause | Fix |
|-------|-------|-----|
| `HTTP 403` on Graph API | App Registration not owner on App Registration | Add as owner via PowerShell or portal |
| `HTTP 403` on SharePoint | Sites.Selected not granted for site | Run Graph Explorer POST to grant site permission |
| `HTTP 400` on SharePoint | Wrong `SHAREPOINT-SITE-ID` format | Use full 3-part composite ID from Graph API |
| `Secrets Found: 0` | Federated credential not working | Check `CROSS-TENANT-APP-ID` and `CROSS-TENANT-TENANT-ID` in Key Vault |
| `Rows Scanned: 0` on rotation | Wrong `OWNER-EMAILS` value | Must match `AppOwners` column value in SharePoint |
| `api://AzureADTokenExchange` error | Federated credential not configured | Check UAMI object ID matches subject in federated credential |
