# Azure Secret Governance

An automated system that monitors Azure App Registration client secrets across your tenant,
raises Jira incidents, sends Teams alerts, and rotates expiring secrets on a weekly schedule —
with no manual intervention.

> The system runs as two containers inside a single Azure Container App, triggered weekly by
> Azure Automation Runbooks. All credentials are managed via a User-Assigned Managed Identity
> — no client secrets stored in code or config files.

---

## What this delivers

- **Scans** all App Registrations in your Entra ID tenant and classifies secrets by urgency
- **Raises Jira tickets** automatically with the right severity (P1/P2/P3)
- **Sends Teams Adaptive Card alerts** to the configured channel with days remaining
- **Rotates secrets** for P1/P2/P3 apps automatically and stores new values in Key Vault
- **Updates SharePoint** with a live audit trail — every secret has a row showing its full lifecycle
- **Closes the loop** via Jira automation — when an engineer resolves the ticket, SharePoint
  updates to `Rotated` within 2–3 seconds. If they reopen it, SharePoint resets automatically.

## Secret severity levels

| Bucket | Days remaining | Severity | What the system does |
|--------|---------------|----------|--------------------|
| **P1** | 0 – 7 days | CRITICAL | Jira + Teams alert + SharePoint + Auto-rotation |
| **P2** | 8 – 30 days | WARNING | Jira + Teams alert + SharePoint + Auto-rotation |
| **P3** | 31 – 60 days | INFO | Jira ticket + SharePoint + Auto-rotation |
| **P4** | 61+ days | SAFE | Written to SharePoint with owners stamped — no alert |
| **ExpiredManualReview** | -1 to -7 days | EXPIRED | Jira + Teams alert — **NOT auto-rotated** |
| **Ignore** | -8+ days | — | Completely skipped — not written to SharePoint |

<Callout type="warning">
  **ExpiredManualReview secrets are never auto-rotated.** A secret that has already expired
  may be actively in use by an application that will break on rotation without coordination.
  The system flags it for human review instead.
</Callout>

## Permission model

The system uses exactly two Microsoft Graph permissions:

| Permission | What it allows |
|-----------|---------------|
| `Application.ReadWrite.OwnedBy` | Read ALL App Registrations (reads are unrestricted). Write — create new secrets — only on apps where UAMI is listed as owner |
| `Sites.Selected` | Read/write the SecretAlertRegistry SharePoint list only |

This is least-privilege by design. The UAMI must be manually added as an owner on each
App Registration it should manage — providing a natural security boundary at the Entra level.

---

## Ownership model

The system uses a two-gate ownership model:

```
Gate 1 — Entra ownership (API level, enforced by Microsoft)
  UAMI must be listed as owner on the App Registration
  If not owner → addPassword returns 403 → cannot rotate

Gate 2 — SharePoint AppOwners column (code level, enforced by system)
  Discovery stamps Entra owners to the AppOwners column
  Monitoring/rotation filter by KV OWNER-EMAIL value
  If not in AppOwners → row skipped
```

Both gates must pass for a secret to be monitored and rotated.
