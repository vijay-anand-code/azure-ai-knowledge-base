# Azure Secret Governance

This system watches Azure App Registration client secrets across two Entra ID tenants, opens
Jira tickets, sends Teams alerts, and rotates secrets before they expire. It runs on a weekly
schedule and doesn't need manual intervention, apart from one approval step a human does per
app before that app's secrets get **rotated**.

The system runs as two containers inside a single Azure Container App, triggered weekly by
Azure Automation Runbooks. Credentials are handled through a User-Assigned Managed Identity, so
there are no client secrets sitting in code or config files.

<Callout type="warning">
  `DevSecOpsOwnership` gates **rotation only**, not monitoring. Every secret gets discovered,
  tracked, re-classified into a bucket, and gets its Jira ticket/Teams alert every run regardless
  of ownership, since monitoring's own code explicitly removed that gate on ticket/alert creation,
  per an explicit client requirement that alerting fire purely on severity. The only place ownership
  still blocks real action is `devsecops-secret-governance-secret-rotation.py`, which genuinely
  skips a row (counted as `rowsSkippedNoManualOwner`) if `DevSecOpsOwnership` is blank when it
  gets there. Monitoring still counts unowned rows (`skippedNotOwned`), but that's purely
  informational now: it doesn't affect what monitoring actually does with the row. More on how
  `DevSecOpsOwnership` gets filled in the ownership model section below.
</Callout>

<Callout type="warning">
  `ManualAppOwners` was renamed to `DevSecOpsOwnership` and the Jira custom fields were
  restructured (`TeamName`/`ProductName` recreated as dropdowns, `DevSecOpsOwnership` removed
  from Jira entirely, four new fields added: `ProductTeamsKeyVaultName`, `NewSecretVaultName`,
  `NewSecretKeyId`, `NewSecretPresent`). If you're reading an older printout or screenshot with
  `ManualAppOwners`, treat it as `DevSecOpsOwnership`: same column, same purpose, new name.
</Callout>

## What this delivers

- Scans all App Registrations across both configured Entra ID tenants and classifies every
  secret by urgency (P1 through P4)
- Raises Jira tickets for every bucket except P4 (safe), with the ticket's priority field set to
  the literal bucket name (P1, P2, or P3)
- Sends Teams alerts to the configured channel with days remaining. Within P1, the 0 to 3 day
  half additionally tags a specific person, the 4 to 7 day half sends a plain alert with no tag
- Rotates secrets for P1 through P3 apps automatically once `DevSecOpsOwnership` is set, and
  stores the new values in Key Vault with a configurable validity period. If a row's
  `ProductTeamsKeyVaultName` is filled in, the rotated value goes into that specific Key Vault
  instead of the shared rotation vault. If `NewSecretKeyId` already has a value when rotation
  reaches that row (meaning an engineer already generated and recorded the new secret manually
  via Jira's `NewSecretPresent` field), rotation skips generating a second, conflicting one
- Looks up a Key Vault secret named after a row's `ProductName` column, if filled in, and writes
  that secret's value into `DevSecOpsOwnership` automatically, overwriting whatever was there.
  The local `sync.py` script does a related but distinct lookup, see the ownership model
  section below for the difference
- Populates `AppOwners`, `TenantID`, and `ObjectID` from live Entra data on every row it touches,
  not just at first discovery, so a manually-corrected or stale value self-heals back to whatever
  Entra actually reports on the next run
- Keeps a SharePoint audit trail across two lists: `SecretAlertRegistry` for anything actionable,
  `IgnoredSecretRegistry` for secrets that are genuinely expired and abandoned
- Backs up both lists before every monitoring run touches them: the current state is snapshotted
  into a dedicated backup list, and whatever was previously in that backup list is archived to a
  Storage Account as CSV first, before being overwritten. See the SharePoint page for details
- Checks for abandoned secrets. A secret past 8 days expired with no open Jira ticket, or with a
  canceled one, moves to `IgnoredSecretRegistry`. One that's still being worked stays visible and
  gets marked overdue instead of disappearing
- Closes the loop through a Jira automation rule. The live workflow currently has four statuses
  (To Do, In Progress, Waiting for Customer, Resolved), and SharePoint updates on every one of them,
  not only when a ticket resolves. A second workflow validator, separate from the field-required
  gate on Resolved, now also requires `TeamName`/`ProductName`/`ProductTeamsKeyVaultName`/
  `NewSecretPresent` before a ticket can even leave To Do

## Architecture

```

                       the resolved identity as a real Entra owner
  00:30  Monitoring   backs up both SharePoint lists first, then raises Jira tickets and Teams
                       alerts, propagates DevSecOpsOwnership, re-stamps AppOwners/TenantID/

|                              memory                     |

|                              Jira Automation has one     |
|                              stable external URL         |
|                                                         |
|  Container 2: Monitor REST API (port 8001, internal)    |
|    POST /tools/run_secret_monitoring                    |

|    POST /tools/create_jira_ticket                       |
```

<Callout type="info">
  Container 1's earlier `/jira-webhook` endpoint has been retired. Jira's automation rule now
  calls Container 1's `/jira-status-update` proxy, which forwards internally to Container 2's
  `/tools/jira-status-update`. That keeps one source of truth for the Jira to SharePoint sync,
  instead of two endpoints doing overlapping work that could drift apart from each other over
  time, while still giving the automation rule one stable external URL to call.
</Callout>

## Secret severity levels

| Bucket | Days remaining | Severity | What the system does |
|--------|---------------|----------|--------------------|
| **P1**, 0 to 3 days | 0 to 3 days | CRITICAL | Jira ticket, Teams alert tagging a specific person, auto rotation |
| **P1**, 4 to 7 days | 4 to 7 days | CRITICAL | Jira ticket, Teams alert with no tagging, auto rotation |
| **P2** | 8 to 30 days | WARNING | Jira ticket, Teams alert, auto rotation |
| **P3** | 31 to 60 days | INFORMATION | Jira ticket only, no Teams alert, auto rotation |
| **P4** | 61+ days | SAFE | Written to `SecretAlertRegistry` with owners stamped. No alert, no ticket, no rotation |
| **ExpiredManualReview** | expired 1 to 7 days ago | EXPIRED | Jira ticket and Teams alert. Not auto rotated |
| **Ignore, subject to the abandonment check** | expired 8+ days ago | none | See below, this one isn't simply skipped |

<Callout type="info">
  0 to 3 days and 4 to 7 days are both bucket **P1**, not two separate buckets. Both halves raise
  a Jira ticket and send a Teams alert, the only difference is whether the alert tags a specific
  person. This replaced an older five-bucket scheme (P1 0 to 3, P2 4 to 7, P3 8 to 30, P4 31 to
  60, P5 61+) where the tagged and untagged halves were separate buckets, P1 and P2. Every bucket
  name from the old P3 down has shifted: old P3 is now P2, old P4 is now P3, old P5 (safe) is now
  P4.
</Callout>

<Callout type="warning">
  ExpiredManualReview secrets are never auto rotated. A secret that's already expired might
  still be in active use by an application that would break on rotation without coordination,
  so the system flags it for a human to review instead.
</Callout>

### What actually happens past 8 days expired

A secret this old doesn't get dropped from tracking just because of the day count. That would
risk losing visibility on something someone is actively rotating right now. The decision
depends on whether there's still a live, open Jira ticket for it:

- No ticket at all: genuinely abandoned, moved to `IgnoredSecretRegistry` (the code also handles
  a canceled ticket the same way, but the live KAN workflow has no Canceled status, so that
  specific trigger never actually fires today, see the Jira Automation page)
- Ticket is Resolved but the row was never marked Rotated: flagged as a possible sync gap and
  left visible for someone to look into, rather than quietly disappearing
- Ticket is In Progress, To Do, or Waiting for Customer (the live KAN workflow's only three
  non-terminal statuses): someone's actively working it, so the row stays in
  `SecretAlertRegistry`, `AlertStatus` set to `OverdueManualReview`, not auto ignored

<Callout type="warning">
  P1, P2, and P3 all raise a Jira ticket, and so does ExpiredManualReview. An earlier version of
  this system left the tagged and untagged halves of what is now P1 out of ticket creation
  entirely (they were separate buckets, P1 and P2, at the time), so a secret with 4 days
  remaining could send a correctly worded critical Teams alert with no ticket behind it at all.
  That's been found and fixed. Every bucket except P4 (safe) reliably gets a ticket now.
</Callout>

## Permission model

The system federates one managed identity to a single App Registration, used the same way
across discovery, monitoring, and rotation. Using exactly one App Registration is a deliberate
requirement here, not a split into separate ones by privilege level.

| Permission | What it allows |
|-----------|---------------|
| `Application.ReadWrite.OwnedBy` | Read every App Registration across both configured tenants. Write, meaning creating new secrets, only on apps where the managed identity is already listed as an owner |
| `Sites.Selected` | Read and write all four SharePoint lists: `SecretAlertRegistry`, `SecretAlertRegistryBackup`, `IgnoredSecretRegistry`, and `IgnoredSecretRegistryBackup` |

This is least privilege by design. The identity has to be manually added as an owner on each
App Registration it should rotate. `OwnedBy` can't grant new ownership on its own, so the
automation itself is never able to do that step. Granting ownership stays a separate, deliberate
human action, done from a laptop under the operator's own signed in session rather than by the
shared automation identity, so that particular privileged action is always tied to a real person
rather than a shared service principal.

## Ownership model

The system uses one explicit gate, `DevSecOpsOwnership`, filled in one of three ways: two run
inside the container app automatically, and one is a separate local script with a materially
different design.

**Directly.** A human fills in `DevSecOpsOwnership` on any single secret row belonging to an
app. Discovery never writes to this column, so whatever's typed in stays untouched. Monitoring
then copies that value onto every other row for the same app automatically.

**Via `ProductName`, resolved by monitoring.** `decision_engine.py`'s `get_product_service_principal()`
looks up a Key Vault secret named exactly after the row's `ProductName` and writes the secret's
value into `DevSecOpsOwnership`, always overwriting whatever was there. Any `ProductName` value
is tried directly, and there's no allowlist gate on this path. A `ProductName` with no matching Key
Vault secret just leaves `DevSecOpsOwnership` as it was, it doesn't fail the run.

**Via `ProductName`, resolved by the local `sync.py` script.** A materially different mechanism
from monitoring's: this is not a per-product secret lookup at all. `sync.py` reads a single
flat, comma-separated allowlist of `ProductName` values from the `ALLOWED-PRODUCT-NAMES` Key
Vault secret. If a row's `ProductName` is non-blank and appears in that allowlist,
`DevSecOpsOwnership` is set to one fixed, hardcoded identity, `devsecops-secret-governance-monitor`,
never a per-product-resolved value, never a list. If `ProductName` is blank or not in the
allowlist, `DevSecOpsOwnership` is actively **cleared**. Either way, the write only happens when
the current value differs from the desired one, but "differs" cuts both ways: this **will**
overwrite a manually-typed value in either direction (set it to the fixed identity, or wipe it
blank), it is not a fill-if-blank operation. This script also does something the container-app
path never does: for rows where the product is allowed, it adds that same fixed identity as a
**real Entra owner** on the App Registration, using the operator's own signed-in `az login`
session rather than the shared automation identity, one tenant at a time, pausing between
tenants for the operator to switch their `az login` session.

<Callout type="warning">
  `DevSecOpsOwnership` no longer gates monitoring at all: not row creation, not re-classification
  into a new bucket, not Jira ticket creation, not Teams alerts. Monitoring's own code explicitly
  removed that gate (an explicit client requirement: severity alone decides whether something
  gets a ticket). Monitoring still counts unowned rows via a `skippedNotOwned` metric, but that's
  informational only now, not a real skip. The only place ownership genuinely blocks action today
  is rotation (`devsecops-secret-governance-secret-rotation.py`): a row with `DevSecOpsOwnership`
  blank is skipped there and counted as `rowsSkippedNoManualOwner`. So in practice: an unowned
  secret still gets tracked, ticketed, and alerted on schedule; it just never gets rotated until
  someone sets ownership.
</Callout>

`AppOwners`, re-stamped from live Entra data on every row monitoring touches (not just at first
discovery), is a separate column kept for reference only: it shows the *actual* current Entra
owners of the App Registration, as display names rather than emails for user owners, and never
gates anything. An earlier version of this system gated on `AppOwners` matching a fixed list of
emails configured in Key Vault; that filter has been fully replaced by `DevSecOpsOwnership`.
