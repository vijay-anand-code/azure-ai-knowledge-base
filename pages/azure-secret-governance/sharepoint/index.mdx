# SharePoint Setup

The `SecretAlertRegistry` SharePoint list is the central audit trail for all monitored secrets.
Every App Registration secret gets a row here — the system updates it automatically as secrets
move through their lifecycle from discovery → monitoring → rotation → resolved.

## Create the SharePoint site

<Steps>

### Create a team site

- Go to [sharepoint.com](https://sharepoint.com) → **+ Create site → Team site**
- Site name: `Contoso IT` *(or your preferred name)*
- Click **Next → Finish**

### Get the Site ID and List ID

Run this in Graph Explorer or Azure CLI logged in as your admin:

```bash
# Replace <hostname> with e.g. contoso.sharepoint.com
# Replace <sitename> with your site name e.g. ContosoIT
az rest --method get \
  --url 'https://graph.microsoft.com/v1.0/sites/<hostname>:/sites/<sitename>' \
  --query id -o tsv
```

Output format — copy the **full string** including both GUIDs and commas:
```
contoso.sharepoint.com,eb7d38df-4022-4b6a-91ac-10f177c65098,d35b6bd8-064b-49c1-8f15-b1ad9aaf23c1
```

<Callout type="warning">
  Use the full 3-part composite ID as your `SHAREPOINT-SITE-ID` in Key Vault.
  Do not use the Web ID from SharePoint site settings — that is a single GUID and will
  cause HTTP 400 errors when the runbook tries to access the list.
</Callout>

```bash
# After creating the list, get its ID
az rest --method get \
  --url 'https://graph.microsoft.com/v1.0/sites/<SITE_ID>/lists' \
  --query "value[?displayName=='SecretAlertRegistry'].id" -o tsv
```

### Grant App Registration access to the site

The App Registration needs explicit write access to this specific SharePoint site.
Run this in [Graph Explorer](https://developer.microsoft.com/graph/graph-explorer)
signed in as your admin:

```
POST https://graph.microsoft.com/v1.0/sites/<YOUR_SITE_ID>/permissions
```

```json
{
  "roles": ["write"],
  "grantedToIdentities": [{
    "application": {
      "id": "<CROSS_TENANT_APP_ID>",
      "displayName": "azure-secretgovernance-cross-tenant"
    }
  }]
}
```

A successful response returns HTTP 201 with the permission ID. Save the permission ID
in case you need to delete and recreate it later.

<Callout type="info">
  To check existing site permissions at any time:

  ```
  GET https://graph.microsoft.com/v1.0/sites/<YOUR_SITE_ID>/permissions
  ```

  To delete a permission (e.g. to update roles):

  ```
  DELETE https://graph.microsoft.com/v1.0/sites/<YOUR_SITE_ID>/permissions/<permission-id>
  ```
</Callout>

### Create the SecretAlertRegistry list

Inside the team site → **New → List → Blank list**
- Name: `SecretAlertRegistry`
- Click **Create**

### Add all required columns

The `Title` column is already there — rename it to `AppID` first, then add the rest.

<Callout type="warning">
  Column names are case-sensitive. Create them exactly as shown — the system uses these
  names to read and write data via the Graph API.
</Callout>

| Column name | Type | Notes |
|-------------|------|-------|
| **AppID** *(rename Title)* | Single line of text | The App Registration client ID (GUID) |
| **AppName** | Single line of text | Display name of the App Registration |
| **SecretID** | Single line of text | The secret's keyId GUID |
| **SecretDescription** | Multiple lines of text | The secret's display name |
| **ExpirationDate** | Date and time | Date only format |
| **AlertStatus** | Choice | See choices below |
| **AppOwners** | Single line of text | Comma-separated owners stamped by discovery runbook |
| **ObjectID** | Single line of text | App Registration object ID |
| **SeverityLevel** | Single line of text | Auto-set — P1, P2, P3, P4, ExpiredManualReview |
| **ExpiryNotice** | Single line of text | Human-readable e.g. "Secret Expiring in 4 days" |
| **JiraTicketKey** | Single line of text | e.g. KAN-2127 |
| **JiraTicketCreatedDate** | Date and time | Date only format |
| **AlertSentDate** | Date and time | Date only format |
| **LastChecked** | Date and time | Date only format |
| **SecretRotationDetectedDate** | Date and time | Date only format |
| **NewSecretKeyId** | Single line of text | GUID of the newly created secret |
| **NewSecretVaultName** | Single line of text | Key Vault secret name for the new value |
| **TenantID** | Single line of text | Auto-stamped by the system |
| **TenantName** | Single line of text | Auto-stamped by the system |
| **AlertHistory** | Multiple lines of text | Escalation history audit trail |
| **Counter** | Number | Default value: 1 — used for SharePoint Quick Charts |

<Callout type="info">
  **Internal vs Display names:** SharePoint column display names can differ from their
  internal API names. The system always uses the internal name when writing via Graph API.
  Key mappings to be aware of:

  | Display name | Internal name (API) |
  |-------------|-------------------|
  | `SeverityLevel` | `ExpiryBucket` |
  | `SecretRotationDetectedDate` | `RotationDetectedDate` |
  | `AppID` | `LinkTitle` |

  If you rename a column after creating it, the internal name does not change.
  The system uses the internal names — do not worry about renaming display names after setup.
</Callout>

### Configure AlertStatus choices

When creating the `AlertStatus` column, select **Choice** as the type and enter these values
**exactly as shown** — spelling and capitalisation must match:

| Choice value | When the system sets this |
|-------------|--------------------------|
| `Discovered` | Row first created by discovery runbook — not yet actioned by monitoring |
| `JiraRaised` | A Jira incident ticket has been created (P3) |
| `TeamsAlerted` | A Teams alert has been sent (P2) |
| `Escalated` | Secret is critically close to expiry — P1 (0–7 days) |
| `RotatedPendingDeployment` | New secret generated — waiting for team to deploy it |
| `Rotated` | Secret has been rotated and deployment confirmed via Jira close |
| `ExpiredManualReview` | Secret recently expired — requires manual review, NOT auto-rotated |
| `JiraClosed-Unverified` | Jira ticket closed but rotation could not be verified |
| `Resolved` | Secret has been fully resolved |
| `Ignored` | Secret is intentionally excluded from monitoring |

<Callout type="warning">
  A typo in any choice value will cause incorrect system behaviour.
  The system checks these values by exact string match.
</Callout>

### Index the AlertStatus column

Required before the rotation runbook's OData filtering will work. Without indexing,
SharePoint rejects filter queries with HTTP 400.

**SharePoint → SecretAlertRegistry → List settings → Indexed columns → Create a new index**

- Primary column: `AlertStatus`
- Click **Create**

### Enable versioning for audit trail

Versioning keeps a history of every change made to each row — useful for debugging
and compliance.

**SharePoint → SecretAlertRegistry → Settings (gear) → List settings → Versioning settings**

- Create a version each time you edit: **Yes**
- Keep the following number of versions: **50**
- Click **OK**

</Steps>

## How the AppOwners column works

The `AppOwners` column is the key to the ownership model. The discovery runbook reads
every App Registration's owners from Entra ID and stamps them here as a comma-separated string.

```
App Registration: payments-service
Entra owners: vijayanand@contoso.com, azure-secretgovernance-cross-tenant

Discovery stamps to SharePoint:
  AppOwners = "vijayanand@contoso.com, azure-secretgovernance-cross-tenant"
```

The monitoring and rotation runbooks then filter SharePoint rows by this column —
only rows where `AppOwners` contains the value in the `OWNER-EMAIL` Key Vault secret
are actioned. Everything else is skipped.

<Callout type="info">
  If `AppOwners` is blank for a row, that secret will never be monitored or rotated
  until an admin fills it in. The discovery runbook runs weekly and will re-stamp
  it automatically if the App Registration gains an owner in Entra.
</Callout>

## AlertStatus lifecycle

Every secret row follows this lifecycle:

```
Discovery runs
      ↓
AlertStatus = Discovered
      ↓
Monitoring runs
      ↓
P3 → JiraRaised
P2 → TeamsAlerted
P1 → Escalated
      ↓
Rotation runs
      ↓
AlertStatus = RotatedPendingDeployment
NewSecretKeyId = <new key GUID>
NewSecretVaultName = <KV secret name>
      ↓
Engineer deploys new secret
Resolves Jira ticket
      ↓
Jira webhook fires → /jira-webhook
      ↓
AlertStatus = Rotated
SecretRotationDetectedDate = today
```

## SharePoint views to create

Create these filtered views to make the list easier to work with:

| View name | Filter | Purpose |
|-----------|--------|---------|
| **Needs Action** | AlertStatus = Discovered | Newly discovered secrets not yet processed |
| **Critical Secrets** | SeverityLevel = P1 | Secrets expiring within 7 days |
| **Expiring This Month** | SeverityLevel = P2 or P3 | Secrets expiring within 30–60 days |
| **Pending Deployment** | AlertStatus = RotatedPendingDeployment | Rotated but not yet deployed |
| **All Items** | None | Full list — all secrets all statuses |

## Get all column internal names

To verify internal names of all columns in your list, run this in Graph Explorer:

```
GET https://graph.microsoft.com/v1.0/sites/<SITE_ID>/lists/<LIST_ID>/columns?$select=name,displayName
```

This returns every column's `name` (internal API name) and `displayName` (what you see in SharePoint).

## Clean up all rows (reset)

To fully reset the SharePoint list — for example before a fresh test run — use the
`runbook_cleanup_sharepoint.py` runbook:

```
Azure Portal → Automation Account → Runbooks
→ runbook_cleanup_sharepoint → Start
```

After cleanup, run `runbook_discovery` immediately to repopulate the list.

<Callout type="warning">
  This permanently deletes all rows. Only run it on a test environment or when
  you intentionally want to start fresh.
</Callout>

## Troubleshooting

| Error | Cause | Fix |
|-------|-------|-----|
| `HTTP 403` on SharePoint | App Registration not granted site access | Run the Graph Explorer POST to grant site permissions |
| `HTTP 400` on SharePoint | Wrong `SHAREPOINT-SITE-ID` format | Use full 3-part composite ID — not the Web ID |
| `Field not recognized` error | Column internal name mismatch | Run the GET columns query to verify internal names |
| `AlertStatus` filter failing | Column not indexed | Index the AlertStatus column in List settings |
| `AppOwners` blank after discovery | App Registration not listed as Entra owner | Add App Registration as owner on the App Registration in Entra |
| Rows not actioned by monitoring | `OWNER-EMAIL` doesn't match `AppOwners` | Ensure `OWNER-EMAIL` in Key Vault matches the App Registration display name exactly |
