# SharePoint Setup

Four SharePoint lists, all on the same site. Two are the actual working data, and two are
backup copies that **monitoring** (not discovery) refreshes every run. Nothing else in this
system writes anywhere else in SharePoint.

| List | What it holds |
|------|---------------|
| `SecretAlertRegistry` | Every secret in buckets P1 through P4, the active, working list |
| `SecretAlertRegistryBackup` | A snapshot of `SecretAlertRegistry`, taken right before each monitoring run changes anything |
| `IgnoredSecretRegistry` | Secrets expired 8 or more days, confirmed abandoned |
| `IgnoredSecretRegistryBackup` | A snapshot of `IgnoredSecretRegistry`, same timing as above |

<Callout type="info">
  Only the most recent run's snapshot is ever kept in either backup *list* — but nothing is
  actually lost. The rotation order is deliberately **archive, then write, then delete old**:

  1. Whatever is currently sitting in the backup list is archived first, as a CSV blob, to the
     `secret-governance-backups` container of the Storage Account named in the `BACKUP-STORAGE-ACCOUNT-URL`
     Key Vault secret — one blob per run, named `<ListLabel>_<EST timestamp>.csv`.
  2. Only after that archive succeeds does monitoring write a fresh snapshot of the live list
     into the backup list as new rows.
  3. Only once that new snapshot is fully written are the old backup-list rows deleted.

  If the Storage upload is configured but actually fails, the whole run aborts without touching
  anything further — that's treated as a real failure, not a missing-config case. If
  `BACKUP-STORAGE-ACCOUNT-URL` isn't set at all, the Storage step is skipped outright and the
  previous backup-list snapshot is simply discarded once the new one is written — SharePoint
  itself never goes without a backup, but there's no deeper history beyond it in that case.
</Callout>

## Create the site

<Steps>

### Create a SharePoint site

Go to your SharePoint admin center and create a new Team site, or use an existing one. Note
its URL, you will need it for the site ID lookup later.

### Create SecretAlertRegistry

Create a custom list named exactly `SecretAlertRegistry`. Add these columns:

| Column name | Type | Notes |
|-------------|------|-------|
| `Title` | Single line of text | Holds the App ID, not a descriptive title |
| `AppName` | Single line of text | |
| `SecretID` | Single line of text | The secret's key ID from Entra |
| `SecretDescription` | Single line of text | |
| `ExpirationDate` | Single line of text | Stored as a formatted string, not a native date column |
| `ExpiryBucket` | Single line of text | P1 through P4, ExpiredManualReview, or Ignore |
| `ExpiryNotice` | Single line of text | Human readable notice text, refreshed every run |
| `AlertStatus` | Single line of text | See the status lifecycle below |
| `AppOwners` | Single line of text | Re-stamped from live Entra data on every row monitoring touches, not just at first discovery. Reference only, does not gate anything |
| `DevSecOpsOwnership` | Single line of text | Gates rotation only (see warning below). Filled in one of three ways: directly by a person; by `decision_engine.py`'s `get_product_service_principal()`, which looks up any `ProductName` as a Key Vault secret name with no allowlist gate; or by the local `sync.py` script, which checks `ProductName` against a flat `ALLOWED-PRODUCT-NAMES` Key Vault allowlist and, if allowed, sets this column to one fixed identity (`devsecops-secret-governance-monitor`) and also adds that same identity as a real Entra owner — clearing the column if the product isn't allowed. See the [Ownership model](/azure-secret-governance#ownership-model) section for the full breakdown. Discovery never writes to it |
| `ProductName` | Choice | Optional. If filled in, monitoring's `decision_engine.py` looks up a Key Vault secret named exactly this and writes its value, a service principal name, into `DevSecOpsOwnership`, always overwriting whatever was there. The local `sync.py` script uses this column completely differently — as a flat allowlist membership check, not a per-product secret lookup — see the Ownership model section for the difference |
| `ProductTeamsKeyVaultName` | Choice | Optional. If filled in, rotation appends the standard `.vault.azure.net/` suffix to this value and stores the app's newly rotated secret there instead of the shared rotation Key Vault. This is a vault *name* (e.g. `kv-product-a`), not a URL |
| `ObjectID` | Single line of text | The app's Entra object ID, not its App ID |
| `TenantID` | Single line of text | Which of the configured tenants this app actually lives in |
| `TeamName` | Choice | Optional, feeds into rotation's generated secret name (`ProductName-TeamName-AppName`) when `NewSecretVaultName` is blank. Doesn't gate or route anything on its own |
| `JiraTicketKey` | Single line of text | |
| `JiraTicketCreatedDate` | Single line of text | |
| `AlertSentDate` | Single line of text | |
| `LastChecked` | Single line of text | Refreshed on every run that touches this row |
| `AlertHistory` | Multiple lines of text | A running log of escalation events for this row |
| `RotationDetectedDate` | Single line of text | |
| `NewSecretKeyId` | Single line of text | Set once rotation creates a new secret. Also what monitoring's lineage tracking matches a rotated secret's brand-new row against, to carry `TeamName`/`ProductName`/`ProductTeamsKeyVaultName` forward automatically (see the warning below — this carry-forward currently has a bug) |
| `NewSecretVaultName` | Single line of text | The Key Vault secret name a rotated value is stored under. Filled in by the team ahead of the first rotation if the app expects a specific, unchanging name; if left blank, rotation generates one and writes it back here so every later rotation reuses it as a new version |

<Callout type="warning">
  `DevSecOpsOwnership` gates **rotation only**. Monitoring's ownership gate was explicitly removed
  — every row still gets tracked, ticketed, and alerted on severity alone regardless of ownership.
  Rotation (`devsecops-secret-governance-secret-rotation.py`) still genuinely skips a row with
  `DevSecOpsOwnership` blank. `AppOwners` looks similar and is easy to confuse with
  `DevSecOpsOwnership`, but it is only a reference column showing Entra's actual current owners,
  and it does not gate anything.
</Callout>

<Callout type="warning">
  `ProductName`, `TeamName`, and `ProductTeamsKeyVaultName` must be **single-select** Choice
  columns, not multi-select. A multi-select Choice field returns an array from Graph instead of a
  plain string, which breaks every piece of code that reads these columns as text (rotation's
  name generation, the Key Vault lookups, lineage matching). The option text you define also has
  to match exactly, case-sensitive, whatever the code looks it up against: a Key Vault secret
  name for `ProductName`, and the actual Key Vault's name (not its full URL) for
  `ProductTeamsKeyVaultName`, since rotation derives the URL by appending the standard
  `.vault.azure.net/` suffix to whatever's selected.
</Callout>

<Callout type="error">
  **Known bug, not yet fixed in code:** `decision_engine.py`'s lineage carry-forward (the logic
  that copies `TeamName`/`ProductName`/`ProductTeamsKeyVaultName` onto a newly-rotated secret's
  brand-new row) reads and writes the column as `ProductTeamkeyVaultName` — missing the "s" in
  "Teams". Everywhere else that touches this column — the rotation script's vault-routing lookup,
  and `main.py`'s Jira custom-field backfill — uses `ProductTeamsKeyVaultName` (with the "s"),
  which is almost certainly the actual SharePoint column name. Net effect: after a secret's first
  rotation, the lineage step silently writes the carried-forward value into a column that doesn't
  exist / nothing else reads, so the new row's vault routing silently falls back to the shared
  rotation vault instead of the product-specific one, with no error. Worth a code fix in
  `decision_engine.py` (search for `ProductTeamkeyVaultName`, three occurrences) rather than a
  docs-only workaround.
</Callout>

## Status lifecycle

`AlertStatus` on `SecretAlertRegistry` moves through these values over a secret's life:

```
Discovered
   |
   v
JiraRaised  or  TeamsAlerted  or  Escalated  or  CriticalTagged
   |  (depends on bucket, see the runbooks page for which bucket maps to which)
   v
RotatedPendingDeployment
   |
   v
Rotated
```

One status sits outside that normal flow, set only by the Jira automation rule, not by
discovery, monitoring, or rotation:

| Status | What it means |
|--------|---------------|
| `AwaitingReporter` | The Jira ticket is in Waiting for Customer. Monitoring pauses alerts and escalation on this row until the ticket moves to a different status |

<Callout type="info">
  The `jira-status-update` endpoint's code also recognizes a `Blocked` status (mapped from a
  Jira "Blocked" status), but the live KAN workflow has no such status — a ticket in this project
  can never actually put a row into `Blocked`. See the [Jira Automation](/azure-secret-governance/jira)
  page for the full explanation of which statuses are real versus defensively supported.
</Callout>

And these appear only if something needed manual attention rather than following the normal flow:

| Status | What it means |
|--------|---------------|
| `ExpiredManualReview` | The secret expired 1 to 7 days ago. Jira ticket raised at literal `P1` priority, Teams alert sent, never auto-rotated |
| `OverdueManualReview` | The secret expired 8 or more days ago, but its Jira ticket is still open (In Progress, To Do, or Waiting for Customer, in this project's real workflow). Stays visible here rather than moving to `IgnoredSecretRegistry`, since someone is already engaged, never auto-rotated |
| `JiraClosed-Unverified` | The Jira ticket closed, but rotation could not confirm the secret was actually deployed. Needs a person to check |
| `Ignored` | There was no Jira ticket at all, or (in a workflow that has a Canceled status, which this one doesn't) the ticket was Canceled. The secret is no longer being tracked here, it moved to `IgnoredSecretRegistry` |

<Callout type="info">
  AwaitingReporter is not a dead end. Once the underlying Jira ticket moves to a different status
  again, monitoring resumes on that row automatically, on its next run. Same for
  `OverdueManualReview` — once its ticket resolves, the row gets marked `Rotated` by the Jira
  automation rule, or moves to `IgnoredSecretRegistry` on monitoring's next abandonment check if
  the ticket goes stale with no further activity.
</Callout>

## How a secret moves between the two working lists

Nothing in this system deletes a secret's history outright. A secret can move from
`SecretAlertRegistry` into `IgnoredSecretRegistry`, and back again, depending on what actually
happens to it.

**Into `IgnoredSecretRegistry`:** once a secret has been expired for 8 or more days, monitoring
checks whether there is still a live Jira ticket for it. If there is no ticket at all, the row is
moved (in a workflow with a real Canceled status, a Canceled ticket would move it too — this
project's workflow doesn't have one, so that specific trigger never fires here). If there is
still an open ticket in In Progress, To Do, or Waiting for Customer, the row stays in
`SecretAlertRegistry` instead, its `AlertStatus` set to `OverdueManualReview`. If the ticket
shows Resolved but the row is somehow still here, that's flagged as a possible sync-gap anomaly
rather than moved — the Jira→SharePoint sync should already have marked it `Rotated`.

**Back into `SecretAlertRegistry`:** if a secret sitting in `IgnoredSecretRegistry` shows up in
a later discovery run with a later expiry date, meaning someone renewed it in Entra, discovery
creates a fresh row for it in `SecretAlertRegistry` and removes the old row from
`IgnoredSecretRegistry`.

## Grant the App Registration access to this site

The App Registration used for Graph access needs to be explicitly granted access to this
specific site, since it uses the `Sites.Selected` permission rather than a tenant wide grant.
See the infrastructure setup page for the exact Graph Explorer steps. That single grant covers
all four lists described here, since it is a site level permission, not one you repeat per
list.

## Finding your list IDs

Every Key Vault secret that points at one of these lists needs the list's actual ID, not its
name. Get it with:

```powershell
az rest --method GET --uri "https://graph.microsoft.com/v1.0/sites/<YOUR_SITE_ID>/lists?`$select=id,displayName" --output json
```

This returns every list on the site with its `id` and `displayName`. Match the `displayName` to
the list you want and copy its `id` into the matching Key Vault secret.

<Callout type="info">
  If you are on Windows PowerShell rather than Bash, the backtick before `$select` is required,
  Graph OData query parameters otherwise get mangled by PowerShell's own variable expansion.
</Callout>

## Verifying row counts match across a list and its backup

Useful after a discovery run, to confirm nothing was lost or duplicated. Since SharePoint's
Graph endpoint for list items does not support `$count` directly, page through and count:

```powershell
az rest --method GET --uri "https://graph.microsoft.com/v1.0/sites/<YOUR_SITE_ID>/lists/<LIST_ID>/items?`$select=id&`$top=999" --output json > items.json
(Get-Content items.json | ConvertFrom-Json).value.Count
```

If the count comes back as exactly 999, there is a further page. Check for `@odata.nextLink` in
`items.json` and follow it the same way, adding its count to the first page's.
