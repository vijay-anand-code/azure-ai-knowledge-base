# Jira Automation

Whenever a Jira ticket moves to a different status, SharePoint updates within seconds, for
every status in the real workflow, not only when a ticket is resolved. If an engineer moves a
ticket to Done after deploying a rotated secret, the SharePoint row updates to `Rotated`. If
someone reopens it, or moves it to Blocked, or Awaiting Reporter, SharePoint reflects that too.
No one needs to manually update SharePoint for any of these transitions.

<Callout type="warning">
  This page describes the current, corrected setup. An earlier version of this integration
  called a `/jira-webhook` endpoint on Container 1 that only recognized three status names and
  silently did nothing for the other three. That endpoint has been retired. If your Jira
  automation rule still points at `/jira-webhook`, update it to call Container 2 directly as
  described below.
</Callout>

---

## Real world example

> Tuesday 14:30. An engineer deploys the new secret for a payments service and resolves the
> Jira ticket by moving it to Done.
>
> Tuesday 14:30:03. The automation rule fires a web request to Container 2.
>
> Tuesday 14:30:05. The SharePoint row updates from `RotatedPendingDeployment` to `Rotated`.
> Done in a couple of seconds, no manual SharePoint update.

> Wednesday 09:00. The engineer realizes they closed the wrong ticket and moves it back to In
> Progress.
>
> Wednesday 09:00:02. The rule fires again. SharePoint resets from `Rotated` to `JiraRaised`,
> so monitoring picks it back up on its next run.

---

## Why this bypasses the chat agent entirely

| Approach | Speed | Cost | Reliability |
|----------|-------|------|-------------|
| Through the chat agent | slow, tens of seconds | a small cost per call | can hit rate limits |
| Direct call to Container 2 | a couple of seconds | no cost | consistently works |

The automation rule calls Container 2 directly. There is no reasoning step involved in
updating one SharePoint field based on a status name, so there is nothing for a chat agent to
add here.

## Get your Container App FQDN

Before setting up the automation rule, get the Container App public URL:

```bash
az containerapp show \
  --name secret-governance-v2 \
  --resource-group <YOUR_RG> \
  --query "properties.configuration.ingress.fqdn" -o tsv
```

This returns something like:
```
secret-governance-v2.<region>.azurecontainerapps.io
```

Use this as `<YOUR_CONTAINER_APP_FQDN>` in the steps below.

## Setup

<Steps>

### Create the Jira automation rule

In Jira, go to:

**Project Settings, Automation, Create rule**

### Configure the trigger

Set the trigger to fire on ticket transitions, and watch every real status in your workflow,
not a subset:

| Field | Value |
|-------|-------|
| **Trigger** | Work item transitioned |
| **To status** | To Do, In Progress, Done, Canceled, Blocked, Awaiting Reporter: Needs more information |

<Callout type="warning">
  Watch all six statuses in this one rule, not just the ones you expect to matter most. A rule
  that only watches Done and In Progress will never fire at all for a ticket moving to Canceled
  or Blocked, and that transition will simply never reach SharePoint. Missing this is the most
  likely reason a status change appears to do nothing.
</Callout>

### Add the web request action

Add an action: **Send web request**

| Field | Value |
|-------|-------|
| **URL** | `https://<YOUR_CONTAINER_APP_FQDN>/tools/jira-status-update` |
| **HTTP method** | POST |
| **Headers** | `Content-Type: application/json` |
| **Body** | See below |

```json
{
  "jira_key": "{{issue.key}}",
  "to_status": "{{destinationStatus.name}}",
  "today": "{{now.format('yyyy-MM-dd')}}"
}
```

<Callout type="info">
  This endpoint expects exactly these three fields, `jira_key`, `to_status`, and `today`, sent
  flat in the request body, not nested inside an `issue` object. `{{destinationStatus.name}}` is
  the correct smart value here, since the endpoint needs to know which status the ticket is
  moving to, not simply that it changed.
</Callout>

### Name and enable the rule

- **Rule name:** something like `Sync ticket status to SharePoint`
- Click **Enable**
- If an older rule already exists pointing at `/jira-webhook`, disable or delete it once the
  new rule is confirmed working, so a single status change cannot fire two webhooks and update
  the same row twice

</Steps>

## How the endpoint works

```
Jira ticket moves to any of the six statuses
      |
      v
POST /tools/jira-status-update   (Container 2, called directly)
      |
      v
Match to_status against the six recognized statuses
      |
      v
Update every SharePoint row whose JiraTicketKey matches jira_key
```

### Status mapping

| Jira destination status | SharePoint AlertStatus | Notes |
|------------------------|----------------------|-------|
| Done | `Rotated` | Also sets the rotation detected date to today |
| Canceled | `Ignored` | The secret is no longer being tracked |
| In Progress, To Do | `JiraRaised` | Monitoring treats the row as reopened and resumes on it |
| Blocked | `Blocked` | Monitoring pauses alerts and escalation on this row until the status changes again |
| Awaiting Reporter: Needs more information | `AwaitingReporter` | Same pause behavior as Blocked |
| Anything else | No update | Logged, in case this is a typo in the rule or a workflow status this endpoint has not been told about yet |

<Callout type="info">
  Blocked and Awaiting Reporter are not a dead end. Once the ticket moves to a different status
  again, the row resumes normal monitoring automatically, since these are treated as paused, not
  finished.
</Callout>

## Verifying the automation works

- Find a Jira ticket with a corresponding SharePoint row in `RotatedPendingDeployment`
- Move the ticket to Done
- Check Project Settings, Automation, Audit log, it should show success
- Check SharePoint, the row should show `AlertStatus: Rotated`
- Repeat for at least one of Canceled, Blocked, or Awaiting Reporter, since these are the
  statuses most likely to have been missed by an older rule's trigger list

### Check container logs if something goes wrong

```bash
az containerapp logs show \
  --name secret-governance-v2 \
  --resource-group <YOUR_RG> \
  --container monitor-mcp \
  --tail 100
```

Look for a line like this:

```
INFO: jira-status-update: item=<id> jira=KAN-2127 -> AlertStatus=Rotated
```

<Callout type="info">
  If Jira shows the rule fired successfully but SharePoint did not update, the most common
  cause is `JiraTicketKey` in SharePoint not matching the ticket key exactly. Check for extra
  spaces or a different key format.
</Callout>

## Jira project setup

Before automation can raise tickets, configure the following in Key Vault:

| Key Vault secret | Example value | Notes |
|-----------------|--------------|-------|
| `JIRA-BASE-URL` | `https://example.atlassian.net` | No trailing slash |
| `JIRA-PROJECT-KEY` | `KAN` | Project, Settings, Details, Key |
| `JIRA-EPIC-KEY` | example ticket key | Optional. Create an epic and copy its key if you want tickets grouped under it |
| `JIRA-ISSUE-TYPE` | `Incident` | Must match exactly, check your project's issue types |
| `JIRA-API-TOKEN` | token value | Create and manage from your Atlassian account security settings |
| `JIRA-USER-EMAIL` | the account that owns the API token | |

<Callout type="warning">
  API tokens expire. If Jira ticket creation starts failing with HTTP 400 or 403, generate a
  new API token from your Atlassian account's security settings and update the `JIRA-API-TOKEN`
  Key Vault secret. Then restart Container 2 to pick up the new value:

  ```bash
  az containerapp revision restart \
    --name secret-governance-v2 \
    --resource-group <YOUR_RG> \
    --revision $(az containerapp revision list \
      --name secret-governance-v2 \
      --resource-group <YOUR_RG> \
      --query "[0].name" -o tsv)
  ```
</Callout>

<Callout type="warning">
  If ticket creation fails with HTTP 400 specifically for P1, P2, P3, or P4 severity secrets,
  check whether those four priority names actually exist in your Jira project's priority
  scheme. The system sets the ticket's priority field to the literal bucket name, and that
  requires priorities named exactly `P1`, `P2`, `P3`, and `P4` to already exist there. Jira's
  own default priorities, like Highest or Medium, do not satisfy this on their own.
</Callout>

## Ticket format

Each ticket the system creates looks like this:

```
[CRITICAL] Azure Secret Expiry - example-service - 2 days remaining

App Registration Name: example-service
App ID: <app-id>
Secret ID: <secret-id>
Secret Description: P2_15d
Expiration: 2026-07-17T00:00:00Z
Days Remaining: 2 days remaining
Severity: CRITICAL
```

When the rotation runbook creates a new secret, it adds a comment:

```
AUTO-ROTATION, 2026-07-15
A new client secret has been generated for example-service.
New credential keyId: <key-id>
New credential expiry: 2027-07-15T00:00:00Z
Stored in Key Vault under: example-service-KAN-2127

Next steps:
1. Retrieve the value from Key Vault (example-service-KAN-2127)
2. Deploy to all dependent services
3. Confirm authentication works
4. Close this ticket to mark as Rotated in SharePoint.
```

## Troubleshooting

| Issue | Cause | Fix |
|-------|-------|-----|
| Rule fires but SharePoint not updated | `JiraTicketKey` mismatch in SharePoint | Check for extra spaces or a different key format |
| A specific status never updates SharePoint | That status is missing from the rule's trigger list | Add it. All six statuses need to be in the trigger, not just the ones you expect to use most |
| HTTP 400 on ticket creation | Jira API token expired, or a P1 to P4 priority name is missing from the project | Regenerate the token, or add the missing priority name to the Jira priority scheme |
| HTTP 403 on ticket creation | Wrong `JIRA-USER-EMAIL` | Must match the account that owns the API token |
| Web request returns 404 | Wrong Container App FQDN, or still pointing at the retired `/jira-webhook` path | Verify the FQDN with the `az containerapp show` command above, and confirm the URL ends in `/tools/jira-status-update` |
| SharePoint not updating on any transition | Wrong smart value in the request body | Use `{{destinationStatus.name}}`, not `{{issue.status.name}}`, and send `jira_key`, `to_status`, and `today` as flat fields, not nested under an `issue` object |
