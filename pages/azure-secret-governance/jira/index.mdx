# Jira Automation

When an engineer resolves a Jira ticket after deploying a rotated secret, SharePoint
automatically updates to `Rotated` within seconds. If they accidentally close the wrong
ticket and reopen it, SharePoint resets to `JiraRaised` so monitoring picks it up again.
No one needs to manually update SharePoint.

---

## Real world example

> **Tuesday 14:30** — Engineer deploys the new secret for `payments-service`.
> They open Jira and resolve ticket `KAN-2127`.
>
> **Tuesday 14:30:03** — Jira automation fires a webhook to the Container App.
>
> **Tuesday 14:30:05** — SharePoint row for `KAN-2127` updates from
> `RotatedPendingDeployment` → `Rotated`. Done in 2 seconds. No manual SharePoint update.

> **Wednesday 09:00** — Engineer realises they resolved the wrong ticket and reopens `KAN-2127`.
>
> **Wednesday 09:00:02** — Webhook fires again. SharePoint resets from `Rotated` → `JiraRaised`.
> Monitoring will pick it up on the next weekly run.

## Why we bypass LangChain for this

| Approach | Speed | Cost | Reliability |
|----------|-------|------|-------------|
| Via LangChain (old) | 30–60 seconds | ~$0.01 per webhook | Hit rate limits (429) |
| Direct Container 2 call (current) | 2–3 seconds | $0 | Always works |

The webhook endpoint calls Container 2 directly — no GPT-4o reasoning needed to update
a SharePoint field.

## Get your Container App FQDN

Before setting up Jira automation, get the Container App public URL:

```bash
az containerapp show \
  --name secret-governance-v2 \
  --resource-group <YOUR_RG> \
  --query "properties.configuration.ingress.fqdn" -o tsv
```

This returns something like:
```
secret-governance-v2.<region>.azurecontainerapps.io
```

Use this as `<YOUR_CONTAINER_APP_FQDN>` in the steps below.

## Setup

<Steps>

### Create the Jira automation rule

In Jira, go to:

**Project Settings → Automation → Create rule**

### Configure the trigger

Set the trigger to fire on ticket transitions:

| Field | Value |
|-------|-------|
| **Trigger** | Work item transitioned |
| **To status** | `RESOLVED`, `IN PROGRESS`, `TO DO` |

<Callout type="info">
  Add all three statuses to a **single rule** — the endpoint handles all transitions
  and decides what SharePoint update to make based on the destination status.
</Callout>

### Add the webhook action

Add an action: **Send web request**

| Field | Value |
|-------|-------|
| **URL** | `https://<YOUR_CONTAINER_APP_FQDN>/jira-webhook` |
| **HTTP method** | POST |
| **Headers** | `Content-Type: application/json` |
| **Body** | See below |

```json
{
  "issue": {
    "key": "{{issue.key}}",
    "fields": {
      "status": {
        "name": "{{issue.status.name}}"
      }
    }
  }
}
```

<Callout type="warning">
  Use `{{issue.status.name}}` — **not** `{{destinationStatus.name}}`.
  The `destinationStatus` smart value does not resolve reliably in all Jira automation contexts
  and will result in an empty status being sent, causing no SharePoint update.
</Callout>

### Name and enable the rule

- **Rule name:** `Trigger Secret Agent on Ticket Close`
- Click **Enable**

</Steps>

## How the webhook endpoint works

```
Jira resolves or reopens ticket
      ↓
POST /jira-webhook  (Container 1 — LangChain agent)
      ↓
Extract: jira_key, status from payload
      ↓
status = "resolved/done/closed"?     status = "in progress/to do/reopened"?
      ↓                                        ↓
POST /tools/update_on_jira_close      POST /tools/jira-status-update
(Container 2 — no GPT-4o)            (Container 2 — no GPT-4o)
      ↓                                        ↓
AlertStatus → Rotated                 AlertStatus → JiraRaised
SecretRotationDetectedDate → today    Monitoring picks it up next run
```

### Status mapping

| Jira destination status | SharePoint AlertStatus | SharePoint field updated |
|------------------------|----------------------|--------------------------|
| `resolved`, `done`, `closed` | `Rotated` | `SecretRotationDetectedDate` = today |
| `in progress`, `to do`, `reopened` | `JiraRaised` | `LastChecked` = today |
| Anything else | No update | Logged only |

<Callout type="info">
  `SecretRotationDetectedDate` is the SharePoint display name. The internal API name
  is `RotationDetectedDate` — the system uses the internal name automatically.
</Callout>

## Verifying the automation works

- Find a Jira ticket with a corresponding SharePoint row in `RotatedPendingDeployment`
- Resolve the ticket in Jira
- Check **Project Settings → Automation → Audit log** — should show SUCCESS
- Check SharePoint — the row should show `AlertStatus: Rotated`

### Check container logs if something goes wrong

```bash
az containerapp logs show \
  --name secret-governance-v2 \
  --resource-group <YOUR_RG> \
  --container langchain-agent \
  --tail 30
```

Look for these lines:

```
INFO: Jira webhook received: KAN-2127 → 'resolved'
INFO: Ticket KAN-2127 closed — updating SharePoint directly (no AI)
INFO: SharePoint updated for KAN-2127: 1 rows marked Rotated
```

<Callout type="info">
  If Jira shows the webhook fired successfully but SharePoint did not update,
  the most common cause is the `JiraTicketKey` field in SharePoint not matching
  exactly. Check for extra spaces or different casing.
</Callout>

## Jira project setup

Before automation can raise tickets, configure the following in Key Vault:

| Key Vault secret | Example value | Notes |
|-----------------|--------------|-------|
| `JIRA-BASE-URL` | `https://yourcompany.atlassian.net` | No trailing slash |
| `JIRA-PROJECT-KEY` | `KAN` | Project → Settings → Details → Key |
| `JIRA-EPIC-KEY` | `KAN-161` | Create an epic named "Secret Governance" and copy its key |
| `JIRA-ISSUE-TYPE` | `Incident` | Must match exactly — check your project's issue types |
| `JIRA-API-TOKEN` | `ATATT3x...` | Atlassian account → Security → Create and manage API tokens |
| `JIRA-USER-EMAIL` | `admin@contoso.com` | The account that owns the API token |

<Callout type="warning">
  **API tokens expire.** If Jira ticket creation starts failing with HTTP 400 or 403,
  generate a new API token at `id.atlassian.com/manage-profile/security/api-tokens`
  and update the `JIRA-API-TOKEN` Key Vault secret. Then restart Container 2 to pick
  up the new value:

  ```bash
  az containerapp revision restart \
    --name secret-governance-v2 \
    --resource-group <YOUR_RG> \
    --revision $(az containerapp revision list \
      --name secret-governance-v2 \
      --resource-group <YOUR_RG> \
      --query "[0].name" -o tsv)
  ```
</Callout>

## Ticket format

Each ticket the system creates looks like this:

```
[CRITICAL] Azure Secret Expiry - payments-service - 2 days remaining

App Registration Name: payments-service
App ID: 312c31c7-871f-4893-9c85-532aa28070f7
Secret ID: d278da9c-d035-4f58-ba9a-fcf6cc336bc8
Secret Description: P2_15d
Expiration: 2026-07-17T00:00:00Z
Days Remaining: 2 days remaining
Severity: CRITICAL
```

When the rotation runbook creates a new secret, it adds a comment:

```
AUTO-ROTATION — 2026-07-15
A new client secret has been generated for payments-service.
New credential keyId: abc123...
New credential expiry: 2027-07-15T00:00:00Z
Stored in Key Vault under: payments-service-KAN-2127

Next steps:
1. Retrieve the value from Key Vault (payments-service-KAN-2127)
2. Deploy to all dependent services
3. Confirm authentication works
4. Close this ticket to mark as Rotated in SharePoint.
```

## Troubleshooting

| Issue | Cause | Fix |
|-------|-------|-----|
| Webhook fires but SharePoint not updated | `JiraTicketKey` mismatch in SharePoint | Check for extra spaces or different casing in the key |
| HTTP 400 on ticket creation | Jira API token expired | Regenerate token and update Key Vault secret |
| HTTP 403 on ticket creation | Wrong `JIRA-USER-EMAIL` | Must match the account that owns the API token |
| Webhook returns 404 | Wrong Container App FQDN | Verify FQDN using `az containerapp show` command above |
| SharePoint not updating on reopen | Wrong status name in Jira body | Use `{{issue.status.name}}` not `{{destinationStatus.name}}` |
