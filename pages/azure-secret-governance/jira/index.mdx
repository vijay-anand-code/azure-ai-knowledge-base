# Jira Automation

Whenever a Jira ticket moves to a different status, SharePoint updates within seconds, for
every status in the real workflow, not only when a ticket is resolved. No one needs to manually
update SharePoint for any of these transitions.

## Overview

**What triggers it:** a Jira Automation rule fires a web request the moment a ticket transitions.
No polling, no schedule, no AI reasoning involved.

**What it updates:** the matching row's `AlertStatus` in SharePoint, plus a backfill of several
columns from the ticket's custom fields.

**Where it lives:** the endpoint is `/jira-status-update` on **Container 1**. It's a thin proxy
that forwards internally to Container 2's `/tools/jira-status-update`, which does the actual
work.

<Callout type="info">
  **The live workflow has exactly four statuses.** The KAN "IT Helpdesk" project's actual
  workflow, verified directly against Jira, is To Do, In Progress, Waiting for Customer,
  Resolved. The endpoint's code also recognizes Done, Canceled/Cancelled, Blocked, and "Awaiting
  Reporter: Needs more information" as a broader, defensive mapping, but none of those are real
  transitions this project's tickets can ever be moved to. Don't configure the automation trigger
  to watch for them; they can't fire.
</Callout>

<Callout type="warning">
  **This page describes the current, corrected setup.** An earlier version of this integration
  called a `/jira-webhook` endpoint on Container 1 that only recognized three status names and
  silently did nothing for the other three. That endpoint has been retired. If your Jira
  automation rule still points at `/jira-webhook`, or at `/tools/jira-status-update` directly on
  a Container 2 hostname, update it to the URL described in [Setup](#setup) below.
</Callout>

### A real-world example

> Tuesday 14:30. An engineer deploys the new secret for a payments service and resolves the
> Jira ticket by moving it to Resolved.
>
> Tuesday 14:30:03. The automation rule fires a web request to Container 1's proxy, which
> forwards it internally to Container 2.
>
> Tuesday 14:30:05. The SharePoint row updates from `RotatedPendingDeployment` to `Rotated`.
> Done in a couple of seconds, no manual SharePoint update.

> Wednesday 09:00. The engineer realizes they closed the wrong ticket and moves it back to In
> Progress.
>
> Wednesday 09:00:02. The rule fires again. SharePoint resets from `Rotated` to `JiraRaised`,
> so monitoring picks it back up on its next run.

### Why this bypasses the chat agent entirely

| Approach | Speed | Cost | Reliability |
|----------|-------|------|-------------|
| Through the chat agent | slow, tens of seconds | a small cost per call | can hit rate limits |
| Direct call via Container 1's proxy | a couple of seconds | no cost | consistently works |

There is no reasoning step involved in updating one SharePoint field based on a status name, so
there is nothing for a chat agent to add here.

## How it works

### Request flow

```
Jira ticket moves to one of the four real statuses
      |
      v
POST /jira-status-update           (Container 1, plain proxy)
      |
      v
POST /tools/jira-status-update     (Container 2, real handler, internal call)
      |
      v
Match to_status against the recognized statuses (this workflow only ever
sends To Do / In Progress / Waiting for Customer / Resolved)
      |
      v
Not found in the master list?  --yes-->  check IgnoredSecretRegistry too,
      |no                                move any match BACK to the master
      v                                  list (ticket was reopened)
Update every master-list row whose JiraTicketKey matches jira_key
```

### Status mapping

| Jira destination status | SharePoint AlertStatus | Notes |
|------------------------|----------------------|-------|
| Resolved | `Rotated` | Also sets the rotation detected date to today |
| In Progress, To Do | `JiraRaised` | Monitoring treats the row as reopened and resumes on it. If the row was previously moved to `IgnoredSecretRegistry`, it's moved back to the master list first |
| Waiting for Customer | `AwaitingReporter` | Monitoring pauses alerts and escalation on this row until the status changes again |
| Anything else | No update | Logged, in case this is a typo in the rule. This includes Done, Canceled/Cancelled, Blocked, and Awaiting Reporter: the endpoint's code recognizes those names too, but Jira never actually sends them, since none of them are real statuses in this project |

<Callout type="info">
  **Waiting for Customer is not a dead end.** Once the ticket moves to a different status again,
  the row resumes normal monitoring automatically, since it's treated as paused, not finished.
</Callout>

<Callout type="warning">
  **The Canceled path is dead code in this deployment.** The endpoint's code also implements a
  Canceled handler, physically moving a row to `IgnoredSecretRegistry` with a two-way reopen sync
  back to the master list, but Canceled isn't a real status in this project's workflow, so that
  path is currently unreachable from Jira. It's kept because the endpoint may end up serving
  other Jira projects with a different workflow later. Don't rely on tickets in this project ever
  reaching `IgnoredSecretRegistry` via Jira status alone: that only happens through the 8-day
  abandonment check today.
</Callout>

### Field backfill on In Progress and Resolved

On the In Progress and Resolved transitions, the endpoint backfills `TeamName`, `ProductName`,
`ProductTeamsKeyVaultName`, `NewSecretVaultName`, and `NewSecretKeyId` from the Jira custom
fields onto the matching SharePoint row, but only for columns that are still empty; it never
overwrites a value someone already set directly in SharePoint. It fires at both transitions
rather than only In Progress, per an explicit client requirement: a field cleared out after In
Progress would otherwise never get re-synced before the ticket closes.

`NewSecretPresent` itself is never written to SharePoint, since there's no column for it. It
exists only to trigger the acknowledgment comment below. The rotation runbook infers the same
Yes/No distinction later by checking whether `NewSecretKeyId` is already non-empty, so a separate
column was never needed.

<Callout type="info">
  **`NewSecretPresent = No` gets an immediate acknowledgment.** If an engineer marks it at the In
  Progress transition, the endpoint immediately posts a comment on the ticket acknowledging that
  the secret is scheduled for automatic rotation, rather than leaving the engineer with no
  confirmation until the rotation runbook actually runs, which could be a long time later, once
  the secret nears its threshold days.
</Callout>

### To Do &rarr; In Progress workflow gate

The custom fields sent in the web request body only carry real data if Jira actually forces the
engineer to fill them in before the ticket can move. Application code never enforces this: the
endpoint only reads whatever Jira sends it. Enforcement is entirely on the Jira side, via a
combination of a field-required validator and, since KAN is a **team-managed** project (which
has no native "required only if another field equals X" validator), two automation rules doing
conditional validation reactively.

**On the To Do &rarr; In Progress transition, required unconditionally:**

- `TeamName` (customfield_10185) and `ProductName` (customfield_10186) must be set before the
  ticket can leave To Do. Without this, the backfill has nothing to write and the row's
  `TeamName`/`ProductName` stay blank indefinitely.
- `NewSecretPresent` (customfield_10187) must be answered, and `NewSecretVaultPresent`
  (customfield_10191) must be answered. Both are `Yes`/`No` dropdowns; a value of `No` on either
  is a complete, valid answer on its own.

**Conditionally required, enforced by two separate automation rules** (since a plain field-required
validator can't express "only if another field is Yes" in a team-managed project):

1. If `NewSecretPresent` (customfield_10187) is `Yes`, then `NewSecretKeyId` (customfield_10188)
   must be non-blank **and** match the Entra client secret ID format (a GUID:
   `^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$`), not an
   arbitrary string.
2. If `NewSecretVaultPresent` (customfield_10191) is `Yes`, then `NewSecretVaultName`
   (customfield_10189) must be non-blank.

These two are intentionally independent: an engineer can know the target vault before the secret
itself exists (`NewSecretVaultPresent = Yes`, `NewSecretPresent = No`), or vice versa.

<Callout type="warning">
  Team-managed projects can't block a save the way a true field validator does in a
  company-managed project. These two rules are reactive: they trigger on field value changed,
  check the condition, and if it fails, revert the ticket's status and add an explanatory
  comment, rather than preventing the invalid save from happening in the first place.
</Callout>

Without all of this in place, tickets can sit in In Progress with any of these fields blank or
malformed, and the backfill simply has nothing valid to copy: it's a silent no-op per field, not
an error.

## Setup

<Steps>

### Get your Container App FQDN

```bash
az containerapp show \
  --name secret-governance-v2 \
  --resource-group <YOUR_RG> \
  --query "properties.configuration.ingress.fqdn" -o tsv
```

This returns something like:
```
secret-governance-v2.<region>.azurecontainerapps.io
```

Use this as `<YOUR_CONTAINER_APP_FQDN>` in the steps below.

### Create the Jira automation rule

In Jira, go to:

**Project Settings, Automation, Create rule**

### Configure the trigger

Set the trigger to fire on ticket transitions, and watch every real status in your workflow,
not a subset:

| Field | Value |
|-------|-------|
| **Trigger** | Work item transitioned |
| **To status** | To Do, In Progress, Waiting for Customer, Resolved |

<Callout type="warning">
  **Watch all four real statuses in this one rule**, not just the ones you expect to matter most.
  A rule that only watches Resolved and In Progress will never fire at all for a ticket moving to
  Waiting for Customer, and that transition will simply never reach SharePoint. Missing this is
  the most likely reason a status change appears to do nothing.

  Don't add Done, Canceled, Blocked, or Awaiting Reporter to the trigger: they aren't real
  statuses in this project's workflow (Jira's automation UI may not even let you pick them), and
  including them does nothing useful even if it did.
</Callout>

### Add the web request action

Add an action: **Send web request**

| Field | Value |
|-------|-------|
| **URL** | `https://<YOUR_CONTAINER_APP_FQDN>/jira-status-update` |
| **HTTP method** | POST |
| **Headers** | `Content-Type: application/json` |
| **Body** | See below |

```json
{
  "jira_key":                     "{{issue.key}}",
  "to_status":                    "{{issue.status.name}}",
  "today":                        "{{now.jiraDate}}",
  "team_name":                    "{{issue.customfield_10185.value}}",
  "product_name":                 "{{issue.customfield_10186.value}}",
  "product_teams_key_vault_name": "{{issue.customfield_10190.value}}",
  "new_secret_vault_name":        "{{issue.customfield_10189}}",
  "new_secret_key_id":            "{{issue.customfield_10188}}",
  "new_secret_present":           "{{issue.customfield_10187.value}}"
}
```

<Callout type="warning">
  **Dropdown fields need `.value`, plain-text fields don't.** `TeamName`, `ProductName`,
  `ProductTeamsKeyVaultName`, and `NewSecretPresent` are all Jira select-list (dropdown) fields,
  which the API returns as an object (`{id, value, self}`), not a plain string. Interpolating
  `{{issue.customfield_10185}}` bare into the JSON body sends that object through empty or
  malformed, so the SharePoint backfill silently receives nothing even though the ticket's
  dropdown clearly has a value selected. Appending `.value` pulls out just the text
  (`{{issue.customfield_10185.value}}`). `NewSecretVaultName` (`customfield_10189`) and
  `NewSecretKeyId` (`customfield_10188`) are genuine free-text fields and must **not** get
  `.value`, since they're already plain strings. `NewSecretVaultPresent` (`customfield_10191`) is
  a dropdown too, but it's a Jira-only validation gate: it's never sent in this body at all, since
  the backend has no use for it.
</Callout>

<Callout type="info">
  **No `/tools/` prefix.** This hits `/jira-status-update` on Container 1, not
  `/tools/jira-status-update` directly. Container 1 is a plain pass-through proxy in front of
  Container 2's real handler, added so the automation rule has one stable externally-reachable
  URL regardless of which container's port ingress currently points at.
</Callout>

<Callout type="info">
  **Smart value gotchas.** Use `{{now.jiraDate}}` for `today`, not
  `{{now.format('yyyy-MM-dd')}}`: the single-quoted-arg form has been observed to fail with
  "Unable to render smart values" in some Jira environments, which silently kills the whole
  request before it's ever sent.
</Callout>

<Callout type="warning">
  **Use `{{issue.status.name}}` for `to_status`, not `{{destinationStatus.name}}`.**
  `destinationStatus` looks like the more semantically "correct" smart value for a transition
  trigger, and it's the one Atlassian's own examples typically use, but it does not reliably
  resolve in this rule's automation builder: it came through as an empty string on every real
  transition tested, confirmed via raw request logging on the backend, while every `{{issue.*}}`
  value in the same body (all six custom fields, plus `{{now.jiraDate}}`) resolved correctly
  every time. Since a rule's actions run *after* its transition has already completed,
  `{{issue.status.name}}` already reflects the new status by the time this request is built, and
  it's proven reliable here where `destinationStatus` isn't.
</Callout>

<Callout type="warning">
  **Field IDs are project-specific, and they change every time a field is recreated.**
  `customfield_10185`&ndash;`customfield_10191` are this KAN project's *current* field IDs
  (TeamName / ProductName / NewSecretPresent / NewSecretKeyId / NewSecretVaultName /
  ProductTeamsKeyVaultName / NewSecretVaultPresent). These fields were fully deleted and
  recreated at least once during setup, and every recreation assigns brand-new IDs: Jira never
  reuses an old `customfield_NNNNN` number. Don't reuse IDs from an older version of this rule,
  an older screenshot, or an older doc revision without checking them against your project's
  *current* field list (Project Settings, Fields, or by inspecting a real ticket via the API).
  There used to be a field for DevSecOpsOwnership (`customfield_10112` in an earlier iteration);
  it has been removed from Jira entirely and must **not** be sent; ownership is resolved from
  `ProductName` via Key Vault instead (see the
  [Ownership model](/azure-secret-governance#ownership-model) section). All six fields in the
  body are sent on every transition, including ones where they're irrelevant, which is harmless,
  since the endpoint only reads them on In Progress and Resolved. `NewSecretVaultPresent` is
  never sent; it's a Jira-only validation gate, see the workflow gate section above.
</Callout>

### Alert Teams if the web request fails

Add a second branch after the web request action above, so a failed sync doesn't fail silently:

| Field | Value |
|-------|-------|
| **Condition** | `{{webhookResponse.status}}` does not equal `200` |
| **Action** | Send web request |
| **URL** | your `TEAMS-WEBHOOK-URL` Key Vault secret value |
| **HTTP method** | POST |
| **Headers** | `Content-Type: application/json` |

```json
{
  "attachments": [
    {
      "contentType": "application/vnd.microsoft.card.adaptive",
      "content": {
        "type": "AdaptiveCard",
        "$schema": "http://adaptivecards.io/schemas/adaptive-card.json",
        "version": "1.4",
        "body": [
          {
            "type": "TextBlock",
            "text": "Jira Automation failed to sync ticket {{issue.key}} to SharePoint",
            "weight": "bolder",
            "wrap": true
          },
          {
            "type": "TextBlock",
            "text": "Status was {{webhookResponse.status}} when moving to {{issue.status.name}}. Check container logs for jira-status-update.",
            "wrap": true
          }
        ]
      }
    }
  ]
}
```

<Callout type="info">
  This body matches the same Adaptive Card shape `send_teams_alert()` already posts with, so it
  lands in the same Teams channel as every other alert this system sends. Get the webhook URL
  with `az keyvault secret show --vault-name <YOUR_KV_NAME> --name TEAMS-WEBHOOK-URL --query
  value -o tsv`, and treat it like any other credential: it's a bearer secret for that channel,
  don't paste it anywhere outside this rule's own config field.
</Callout>

### Name and enable the rule

- **Rule name:** something like `Sync ticket status to SharePoint`
- Click **Enable**
- If an older rule already exists pointing at `/jira-webhook`, disable or delete it once the
  new rule is confirmed working, so a single status change cannot fire two webhooks and update
  the same row twice

</Steps>

### Jira project configuration

Before automation can raise tickets, configure the following in Key Vault:

| Key Vault secret | Example value | Notes |
|-----------------|--------------|-------|
| `JIRA-BASE-URL` | `https://example.atlassian.net` | No trailing slash |
| `JIRA-PROJECT-KEY` | `KAN` | Project, Settings, Details, Key |
| `JIRA-EPIC-KEY` | example ticket key | Optional. Create an epic and copy its key if you want tickets grouped under it |
| `JIRA-ISSUE-TYPE` | `Incident` | Must match exactly, check your project's issue types |
| `JIRA-API-TOKEN` | token value | Create and manage from your Atlassian account security settings |
| `JIRA-USER-EMAIL` | the account that owns the API token | |

<Callout type="warning">
  **API tokens expire.** If Jira ticket creation starts failing with HTTP 400 or 403, generate a
  new API token from your Atlassian account's security settings and update the `JIRA-API-TOKEN`
  Key Vault secret. Then restart Container 2 to pick up the new value:

  ```bash
  az containerapp revision restart \
    --name secret-governance-v2 \
    --resource-group <YOUR_RG> \
    --revision $(az containerapp revision list \
      --name secret-governance-v2 \
      --resource-group <YOUR_RG> \
      --query "[0].name" -o tsv)
  ```
</Callout>

<Callout type="warning">
  **Priority names must exist in Jira, and only three of them.** If ticket creation fails with
  HTTP 400 specifically for P1, P2, or P3 severity secrets, check whether those three priority
  names actually exist in your Jira project's priority scheme. The system sets the ticket's
  priority field to the literal bucket name, and that requires priorities named exactly `P1`,
  `P2`, and `P3` to already exist there. Jira's own default priorities, like Highest or Medium,
  do not satisfy this on their own. P4 is the safe bucket: it never raises a ticket, so it
  doesn't need a matching priority name.
</Callout>

## Reference

### Ticket format

Each ticket the system creates looks like this:

```
[CRITICAL] Azure Secret Expiry - example-service - 2 days remaining

App Registration Name: example-service
App ID: <app-id>
Secret ID: <secret-id>
Secret Description: P2_15d
Expiration: 2026-07-17T00:00:00Z
Days Remaining: 2 days remaining
Severity: CRITICAL
```

When the rotation runbook creates a new secret, it adds a comment:

```
AUTO-ROTATION, 2026-07-15
A new client secret has been generated for example-service.
New credential keyId: <key-id>
New credential expiry: 2027-07-15T00:00:00Z
Stored in Key Vault under: example-service-KAN-2127

Next steps:
1. Retrieve the value from Key Vault (example-service-KAN-2127)
2. Deploy to all dependent services
3. Confirm authentication works
4. Close this ticket to mark as Rotated in SharePoint.
```

### Troubleshooting

| Issue | Cause | Fix |
|-------|-------|-----|
| Rule fires but SharePoint not updated | `JiraTicketKey` mismatch in SharePoint | Check for extra spaces or a different key format |
| A specific status never updates SharePoint | That status is missing from the rule's trigger list | Add it. All four real statuses need to be in the trigger, not just the ones you expect to use most |
| HTTP 400 on ticket creation | Jira API token expired, or a P1 to P3 priority name is missing from the project | Regenerate the token, or add the missing priority name to the Jira priority scheme |
| HTTP 403 on ticket creation | Wrong `JIRA-USER-EMAIL` | Must match the account that owns the API token |
| Web request returns 404 | Wrong Container App FQDN, or still pointing at the retired `/jira-webhook` path, or at `/tools/jira-status-update` (Container 2's internal-only path) | Verify the FQDN with the `az containerapp show` command above, and confirm the URL is `/jira-status-update` on Container 1, with no `/tools/` prefix |
| SharePoint not updating on any transition, `to_status` logs as an empty string on the backend | `{{destinationStatus.name}}` used for `to_status` instead of `{{issue.status.name}}` | `destinationStatus` doesn't reliably resolve in this automation builder, confirmed via raw request logging. Use `{{issue.status.name}}` instead, and send all nine fields (`jira_key`, `to_status`, `today`, plus the six custom fields) flat, not nested under an `issue` object |
| `today` silently missing / whole request never arrives | `{{now.format('yyyy-MM-dd')}}` failing to render in this Jira environment | Use `{{now.jiraDate}}` instead |
| Backfilled fields (TeamName, ProductName, etc.) never show up in SharePoint | Custom field IDs in the rule body don't match this project's actual field IDs, or the SharePoint column already had a value | Check `customfield_10185`&ndash;`10191` against your project's current field list; they're not portable across Jira projects, and they change every time a field is deleted and recreated. Remember the backfill only fills blank columns, it won't overwrite an existing value |
| Webhook returns 200 and the container logs confirm it processed the row, but TeamName/ProductName/etc. still stay blank | Missing `.value` on a dropdown field's smart value. `{{issue.customfield_10185}}` on a select-list field resolves to nothing usable; the request arrives with an empty string for that field even though the ticket clearly has a value selected | Add `.value`: `{{issue.customfield_10185.value}}`. Applies to TeamName, ProductName, ProductTeamsKeyVaultName, and NewSecretPresent, since those are dropdowns. NewSecretVaultName/NewSecretKeyId are plain text fields and must not get `.value` |
| `NewSecretKeyId` accepted with an obviously wrong value like `1234` | The conditional format-validation rule (`NewSecretPresent = Yes` &rarr; `NewSecretKeyId` must match the GUID pattern) isn't set up yet, or its regex condition is misconfigured | Add the rule described in the To Do &rarr; In Progress workflow gate section above, matching against `^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$` |

## Verifying it works

- Find a Jira ticket with a corresponding SharePoint row in `RotatedPendingDeployment`
- Move the ticket to Resolved
- Check Project Settings, Automation, Audit log, it should show success
- Check SharePoint, the row should show `AlertStatus: Rotated`
- Repeat for Waiting for Customer, since it's the status most likely to have been missed by an
  older rule's trigger list (an older rule watching only Resolved and In Progress would
  never have fired on it at all)

### Check container logs if something goes wrong

```bash
az containerapp logs show \
  --name secret-governance-v2 \
  --resource-group <YOUR_RG> \
  --container monitor-mcp \
  --tail 100
```

Look for a line like this:

```
INFO: jira-status-update: item=<id> jira=KAN-2127 -> AlertStatus=Rotated
```

<Callout type="info">
  **Most common silent-failure cause:** if Jira shows the rule fired successfully but SharePoint
  did not update, check whether `JiraTicketKey` in SharePoint matches the ticket key exactly.
  Extra spaces or a different key format are the usual culprits.
</Callout>
