# Infrastructure Setup

All Azure resources are created with a single Bicep deployment. You do not need to create
anything manually in the portal. The template handles Resource Group, UAMI, Key Vaults,
Container Registry, Container App Environment, and Automation Account.

<Callout type="info">
  You do not need Docker installed. Container images are built directly in Azure using
  `az acr build`, so no local Docker daemon is required.
</Callout>

<Callout type="warning">
  The Bicep templates and exact deployment commands in this page are being reviewed and may not
  match the current version of the templates. Check the actual `infra` folder in the repository
  before running any of the commands below against a real environment.
</Callout>

---

## What gets created automatically

| Resource | What it does |
|----------|-------------|
| **Resource Group** | Container for all project resources |
| **User-Assigned Managed Identity (UAMI)** | The system's identity, authenticates to Key Vault and ACR with no passwords |
| **Key Vault, config** | Stores Jira, Teams, SharePoint, and OpenAI credentials |
| **Key Vault, rotation** | Stores newly generated secret values after rotation |
| **Azure Container Registry** | Stores the Docker images for Container 1 and Container 2 |
| **Container App Environment** | The runtime environment for both containers |
| **Azure Automation Account** | Runs the weekly discovery, monitoring, and rotation runbooks |
| **Log Analytics Workspace** | Captures all container and runbook logs |

## Step-by-step deployment

<Steps>

### Get your Azure Object ID

```bash
az ad signed-in-user show --query id -o tsv
# Example output: 00000000-0000-0000-0000-000000000000
```

### Fill in foundation.parameters.json

```json
{
  "parameters": {
    "location":          { "value": "eastasia" },
    "resourceGroupName": { "value": "example-secret-governance-rg" },
    "prefix":            { "value": "secgov" },
    "adminObjectId":     { "value": "00000000-0000-0000-0000-000000000000" }
  }
}
```

### Run the foundation deployment

```bash
cd secret-governance-infra/infra

az deployment sub create \
  --location eastasia \
  --template-file foundation.bicep \
  --parameters '@foundation.parameters.json'
```

### Create App Registration for cross-tenant access

The system uses a federated credential App Registration instead of granting permissions
directly to the UAMI. This enables cross-tenant access without storing any client secrets.

```bash
# Create the App Registration
az ad app create --display-name "your-cross-tenant-app-name"
# Copy the "appId" from the output, this is your CROSS_TENANT_APP_ID
```

### Add federated credential to App Registration

This tells Azure to trust the UAMI to assert its identity to this App Registration.

```bash
APP_ID="<APP_ID_FROM_PREVIOUS_STEP>"
UAMI_OBJECT_ID="<UAMI_OBJECT_ID>"

cat > /tmp/fed.json << 'EOF'
{
  "name": "ForCrossTenant",
  "issuer": "https://login.microsoftonline.com/<YOUR_TENANT_ID>/v2.0",
  "subject": "<UAMI_OBJECT_ID>",
  "audiences": ["api://AzureADTokenExchange"]
}
EOF

az ad app federated-credential create \
  --id $APP_ID \
  --parameters "@/tmp/fed.json"
```

<Callout type="info">
  The `subject` field must be the object ID of the UAMI, not the client ID.
  Find it in Azure Portal, under Managed Identities, your UAMI, Overview, Object (principal) ID.
</Callout>

<Callout type="warning">
  Do this step once, and only against the tenant where the app registration itself was created,
  the `<YOUR_TENANT_ID>` in the issuer field above. An app registration lives in exactly one
  tenant, wherever you were signed into when you ran `az ad app create` in the previous step.
  Do not repeat this step for additional tenants. When you later add more tenants for scanning,
  they get an enterprise application, a service principal for this same app registration,
  through the admin consent URL below, not a second federated credential or a second app
  registration of their own.
</Callout>

### Add API permissions to the App Registration

Before granting consent, add the three Graph application permissions the app registration
needs. In Azure Portal, go to App Registrations, your cross-tenant app, API permissions, Add a
permission, Microsoft Graph, Application permissions, and add these three:

- `Application.ReadWrite.OwnedBy`, so the app can read every App Registration and write secrets
  only to apps it already owns
- `Sites.Selected`, so the app can read and write the SharePoint lists it is granted against
- `User.ReadBasic.All`, so the app can read the display name of user owners on an App
  Registration. Without this, Graph still returns owner objects, but user owners come back with
  only an id and no name at all, and there is no error to tell you why

### Grant admin consent through the consent URL

The simplest way to both create the enterprise application in a tenant and grant consent for
the permissions above is the standard Microsoft admin consent URL. Sign in as a Global
Administrator or Privileged Role Administrator in the target tenant, then visit:

```
https://login.microsoftonline.com/<TENANT_ID>/adminconsent?client_id=<CROSS_TENANT_APP_ID>
```

This single URL creates the enterprise application for your app registration in that tenant if
it does not already exist, and grants admin consent for whatever permissions are already
configured on the app registration. You do not need to run a separate script for this.

<Callout type="warning">
  If you are scanning more than one tenant, visit this URL once per tenant, signed in as an
  admin of that specific tenant each time. Consent granted in one tenant does not carry over to
  another.
</Callout>

### Verify consent actually landed

Getting the admin consent prompt and clicking through it is a good sign, but worth confirming
directly rather than assuming, especially in a tenant you visited the URL for a while ago. In
that tenant's Azure Portal, go to Enterprise Applications, find your app, Permissions. All
three permissions should show up with Admin consent in the Type column and Granted through
showing Admin consent, not just listed as configured on the app registration. Do this check in
every tenant separately, since each tenant's consent is independent.

<Callout type="info">
  You can also grant permissions and consent through PowerShell instead of the portal and the
  consent URL, if you prefer a scripted, repeatable setup:

  ```powershell
  Connect-MgGraph -Scopes "Application.ReadWrite.All", "AppRoleAssignment.ReadWrite.All"

  $appId      = "<CROSS_TENANT_APP_ID>"
  $appSp      = Get-MgServicePrincipal -Filter "appId eq '$appId'"
  $appSpId    = $appSp.Id
  $graphAppId = "00000003-0000-0000-c000-000000000000"
  $graphSp    = Get-MgServicePrincipal -Filter "appId eq '$graphAppId'"

  $rolesToGrant = @("Application.ReadWrite.OwnedBy", "Sites.Selected", "User.ReadBasic.All")

  foreach ($roleName in $rolesToGrant) {
      $role = $graphSp.AppRoles | Where-Object { $_.Value -eq $roleName }
      New-MgServicePrincipalAppRoleAssignment `
          -ServicePrincipalId $appSpId `
          -PrincipalId        $appSpId `
          -ResourceId         $graphSp.Id `
          -AppRoleId          $role.Id
  }

  Write-Host "Permissions granted"
  ```

  This still needs a separate admin consent step afterward, in Azure Portal under Enterprise
  Applications, your cross-tenant App Registration, Permissions, Grant admin consent.
</Callout>

### Add App Registration as owner on App Registrations

The App Registration must be listed as an owner on each App Registration it should manage.
This is required for `addPassword` to work during rotation. Because `OwnedBy` cannot grant new
ownership on its own, this step always has to be done by a person with the right role, never by
the automation itself.

```powershell
Connect-MgGraph -Scopes "Application.ReadWrite.All"

# Get App Registration service principal object ID
$appRegClientId = "<CROSS_TENANT_APP_ID>"
$appRegSp       = Get-MgServicePrincipal -Filter "appId eq '$appRegClientId'"
$appRegSpId     = $appRegSp.Id

# Add as owner on a specific App Registration
$targetAppObjectId = "<TARGET_APP_REGISTRATION_OBJECT_ID>"
New-MgApplicationOwnerByRef -ApplicationId $targetAppObjectId -BodyParameter @{
    "@odata.id" = "https://graph.microsoft.com/v1.0/directoryObjects/$appRegSpId"
}
```

<Callout type="info">
  Why `OwnedBy` instead of `ReadWrite.All`? `Application.ReadWrite.OwnedBy` allows reading every
  App Registration, but write operations, meaning creating new secrets during rotation, are
  limited to apps where the App Registration is already listed as an owner. That is
  least-privilege by design, and it is also why this project uses one App Registration rather
  than a wider grant. See the owner_sync_local.py note above for how new ownership actually gets
  added.
</Callout>

### Grant App Registration SharePoint site access

`Sites.Selected` restricts access to only the specific SharePoint site you grant it against.
Grant it through Graph Explorer, there is no Azure CLI command for this.

- Go to Graph Explorer at `developer.microsoft.com/graph/graph-explorer`
- Sign in with your admin account
- Get your site ID first:

```
GET https://graph.microsoft.com/v1.0/sites/<tenant>.sharepoint.com:/sites/<site-name>
```

Copy the `id` field from the response, then run:

```
POST https://graph.microsoft.com/v1.0/sites/<YOUR_SITE_ID>/permissions
```

```json
{
  "roles": ["write"],
  "grantedToIdentities": [{
    "application": {
      "id": "<CROSS_TENANT_APP_ID>",
      "displayName": "your-cross-tenant-app-name"
    }
  }]
}
```

<Callout type="info">
  This grant applies at the site level, so it covers all four SharePoint lists the system uses:
  `SecretAlertRegistry`, `SecretAlertRegistryBackup`, `IgnoredSecretRegistry`, and
  `IgnoredSecretRegistryBackup`. You do not need to grant this separately per list.
</Callout>

```bash
az deployment group create \

```

Or set secrets manually through the CLI. See the full reference table below for every secret
the system actually reads, including the ones this deployment step does not cover on its own.

</Steps>

## Permission model

The system uses a federated credential App Registration for all Graph API access.
The UAMI is only used to assert identity, it holds no direct Graph permissions of its own.

| Permission | Granted to | Purpose |
|-----------|------------|---------|
| `Application.ReadWrite.OwnedBy` | App Registration, consented in every tenant being scanned | Read all App Registrations in that tenant. Write secrets only on apps where the App Registration is listed as owner |
| `User.ReadBasic.All` | App Registration, consented in every tenant being scanned | Read the display name of user owners on an App Registration. Without this, user owners come back with an id and no name, and Graph does not return an error to explain why |
| `Sites.Selected` | App Registration, consented in the home tenant | Read and write all four SharePoint lists |
| `Key Vault Secrets User` | UAMI | Read config secrets from Key Vault |
| `Key Vault Secrets Officer` | UAMI | Write new secret values to the rotation Key Vault |
| `AcrPull` | UAMI | Pull container images from Azure Container Registry |

<Callout type="warning">
  Do not grant `Application.ReadWrite.All` or `Sites.ReadWrite.All`. These are broader than
  needed. `Application.ReadWrite.OwnedBy` already covers everything the system does: read every
  app, write only to apps it already owns.
</Callout>

## Runbook schedule

| Time | Runbook | What it does |
|------|---------|-------------|
| `00:00` | `runbook_discovery.py` | Scans every configured tenant, classifies every secret P1 through P4, backs up both SharePoint lists before writing |
| Run manually | `owner_sync_local.py` | Reads `DevSecOpsOwnership` and adds the named identity as an Entra owner. Runs on a laptop, not on the Automation Account, so this step is deliberately outside the schedule |
| `00:30` | `runbook_monitoring.py` | Triggers the monitoring container (via Container 1's `/run`), raises Jira tickets and Teams alerts on severity alone, propagates `DevSecOpsOwnership` to sibling rows |
| `01:00` | `runbook_rotation.py` | Rotates P1 through P3 secrets, stores new values in Key Vault |

<Callout type="info">
  The 30-minute gap between discovery and monitoring gives discovery time to finish writing
  before monitoring reads the same SharePoint list. Owner sync is not on a fixed schedule at
  all, since it needs a person present to run it, not just a trigger.
</Callout>

## Key Vault secrets reference

| Secret name | Example value | Used by |
|-------------|--------------|---------|
| `GRAPH-TENANT-ID` | `00000000-0000-0000-0000-000000000000` | All runbooks |
| `GRAPH-TENANT-NAME` | `example.onmicrosoft.com` | Monitoring container |
| `HOME-TENANT-ID` | `00000000-0000-0000-0000-000000000000` | All runbooks. The tenant where SharePoint actually lives. Falls back to `GRAPH-TENANT-ID` if not set |
| `SHAREPOINT-SITE-ID` | `example.sharepoint.com,site-guid,web-guid` | All runbooks |
| `SHAREPOINT-LIST-ID` | list GUID | All runbooks. `SecretAlertRegistry` |
| `SHAREPOINT-BACKUP-LIST-ID` | list GUID | Discovery. `SecretAlertRegistryBackup` |
| `SHAREPOINT-IGNORED-LIST-ID` | list GUID | Discovery and monitoring. `IgnoredSecretRegistry` |
| `SHAREPOINT-IGNORED-BACKUP-LIST-ID` | list GUID | Discovery. `IgnoredSecretRegistryBackup` |
| `CROSS-TENANT-APP-ID` | app registration client ID | All runbooks |
| `CROSS-TENANT-TENANT-IDS` | comma separated tenant IDs | All runbooks. Plural, replaces the older singular `CROSS-TENANT-TENANT-ID`, which is still read as a fallback if this is not set |
| `SECRET-VALIDITY-DAYS` | `365` | Rotation. How many days a newly rotated secret stays valid for. Falls back to 365 if not set |
| `JIRA-BASE-URL` | `https://example.atlassian.net` | Monitoring and rotation |
| `JIRA-API-TOKEN` | token value | Monitoring and rotation |
| `JIRA-USER-EMAIL` | example account used to authenticate to Jira | Monitoring and rotation |
| `JIRA-PROJECT-KEY` | `KAN` | Monitoring |
| `JIRA-EPIC-KEY` | example ticket key | Monitoring |
| `JIRA-ISSUE-TYPE` | `Incident` | Monitoring |
| `TEAMS-WEBHOOK-URL` | Teams incoming webhook URL | Monitoring |
| `TEAMS-TAG-EMAIL` | example account to mention on P1 (0-3 day) Teams alerts | Monitoring |
| `BACKUP-STORAGE-ACCOUNT-URL` | `https://example.blob.core.windows.net` | Monitoring. Deliberately optional; archives the previous `SecretAlertRegistryBackup`/`IgnoredSecretRegistryBackup` snapshot as CSV before it's overwritten each run. If unset, the old snapshot is simply discarded (with a warning) instead of archived, rather than blocking the run |
| `OWNER-EMAILS` | kept for backwards compatibility only, not used to gate anything by default | Monitoring and rotation |
| `AZURE-OPENAI-ENDPOINT` | `https://example.openai.azure.com` | Container 1 |
| `AZURE-OPENAI-API-KEY` | key value | Container 1 |
| `AZURE-OPENAI-DEPLOYMENT-NAME` | `gpt-4o` | Container 1 |
| `ALLOWED-PRODUCT-NAMES` | comma separated product names | The separate local `devsecops-secret-governance-sync.py` script only, not Container 1 or Container 2. Allowlist gate on which `ProductName` values that script will resolve via its own per-product Key Vault lookup before adding a real Entra owner |

<Callout type="warning">
  `OWNER-EMAILS` and the older singular `OWNER-EMAIL` are no longer what decides which secrets
  get monitored or rotated. That gate is now the `DevSecOpsOwnership` column in SharePoint
  (renamed from `ManualAppOwners`), filled in directly by a person, resolved automatically via a
  `ProductName` Key Vault lookup, or set by the separate local sync script. Discovery never writes
  to that column, and monitoring propagates it to every other row belonging to the same app
  automatically. Ownership no longer gates whether a Jira ticket or Teams alert gets raised,
  only whether monitoring/rotation actively work a row. See the Ownership model section on the
  main page for the full picture.
</Callout>
