# Infrastructure Setup

All Azure resources are created with a single Bicep deployment. You do not need to create
anything manually in the portal — the template handles Resource Group, UAMI, Key Vaults,
Container Registry, Container App Environment, and Automation Account.

<Callout type="info">
  **You do not need Docker installed.** Container images are built directly in Azure using
  `az acr build` — no local Docker daemon required.
</Callout>

---

## What gets created automatically

| Resource | What it does |
|----------|-------------|
| **Resource Group** | Container for all project resources |
| **User-Assigned Managed Identity (UAMI)** | The system's identity — authenticates to Graph API, Key Vault, and ACR with no passwords |
| **Key Vault — config** | Stores Jira, Teams, SharePoint, and OpenAI credentials |
| **Key Vault — rotation** | Stores newly generated secret values after rotation |
| **Azure Container Registry** | Stores the Docker images for Container 1 and Container 2 |
| **Container App Environment** | The runtime environment for both containers |
| **Azure Automation Account** | Runs the weekly discovery, monitoring, and rotation runbooks |
| **Log Analytics Workspace** | Captures all container and runbook logs |

## Step-by-step deployment

<Steps>

### Get your Azure Object ID

```bash
az ad signed-in-user show --query id -o tsv
# Example output: a1b2c3d4-e5f6-7890-abcd-ef1234567890
```

### Fill in foundation.parameters.json

```json
{
  "parameters": {
    "location":          { "value": "eastasia" },
    "resourceGroupName": { "value": "contoso-secret-governance-rg" },
    "prefix":            { "value": "secgov" },
    "adminObjectId":     { "value": "a1b2c3d4-e5f6-7890-abcd-ef1234567890" }
  }
}
```

### Run the foundation deployment

```bash
cd secret-governance-infra/infra

az deployment sub create \
  --location eastasia \
  --template-file foundation.bicep \
  --parameters '@foundation.parameters.json'
```

### Grant UAMI Microsoft Graph permissions

The UAMI needs exactly two Graph API permissions. No more — these two cover everything
the system needs to discover, monitor, and rotate secrets.

```powershell
Connect-MgGraph -Scopes "Application.ReadWrite.All", "AppRoleAssignment.ReadWrite.All"

$uamiSpId   = "<UAMI_SERVICE_PRINCIPAL_OBJECT_ID>"
$graphAppId  = "00000003-0000-0000-c000-000000000000"
$graphSp     = Get-MgServicePrincipal -Filter "appId eq '$graphAppId'"

# Grant Application.ReadWrite.OwnedBy
$role1 = $graphSp.AppRoles | Where-Object { $_.Value -eq "Application.ReadWrite.OwnedBy" }
New-MgServicePrincipalAppRoleAssignment `
    -ServicePrincipalId $uamiSpId `
    -PrincipalId        $uamiSpId `
    -ResourceId         $graphSp.Id `
    -AppRoleId          $role1.Id

# Grant Sites.Selected
$role2 = $graphSp.AppRoles | Where-Object { $_.Value -eq "Sites.ReadWrite.All" }
New-MgServicePrincipalAppRoleAssignment `
    -ServicePrincipalId $uamiSpId `
    -PrincipalId        $uamiSpId `
    -ResourceId         $graphSp.Id `
    -AppRoleId          $role2.Id

Write-Host "✓ Permissions granted"
```

<Callout type="warning">
  Grant admin consent after adding permissions — go to **Azure Portal → App Registrations
  → your UAMI app → API Permissions → Grant admin consent**.
</Callout>

### Add UAMI as owner on App Registrations

The UAMI must be listed as an owner on each App Registration it should manage.
This is a one-time setup per app — do it via PowerShell since the Azure Portal
owner picker only shows users, not managed identities.

```powershell
# Resolve UAMI service principal object ID
$uamiClientId = "<UAMI_CLIENT_ID>"
$uamiSp = Get-MgServicePrincipal -Filter "appId eq '$uamiClientId'"
$uamiObjectId = $uamiSp.Id

# Add UAMI as owner on a specific app
$appObjectId = "<APP_REGISTRATION_OBJECT_ID>"
New-MgApplicationOwnerByRef -ApplicationId $appObjectId -BodyParameter @{
    "@odata.id" = "https://graph.microsoft.com/v1.0/directoryObjects/$uamiObjectId"
}
```

For initial bulk setup across all existing App Registrations, use the
`runbook_bulk_add_uami_owner.py` runbook — it handles all apps in parallel
and skips apps where UAMI is already an owner.

<Callout type="info">
  **Why OwnedBy instead of ReadWrite.All?**
  `Application.ReadWrite.OwnedBy` allows the UAMI to read ALL app registrations
  (reads are unrestricted) but write operations — creating new secrets during rotation —
  are limited to apps where UAMI is listed as an owner. This is least-privilege:
  the system cannot accidentally modify apps it doesn't manage.
</Callout>

### Grant UAMI SharePoint site access

`Sites.Selected` restricts the UAMI to only your specific SharePoint site.
Grant it via Graph Explorer since there is no Azure CLI command for it.

1. Go to [Graph Explorer](https://developer.microsoft.com/graph/graph-explorer)
2. Sign in with your admin account
3. Run this POST:

```
POST https://graph.microsoft.com/v1.0/sites/<YOUR_SITE_ID>/permissions
```

```json
{
  "roles": ["write"],
  "grantedToIdentities": [{
    "application": {
      "id": "<UAMI_CLIENT_ID>",
      "displayName": "uami-secret-monitor"
    }
  }]
}
```

### Populate Key Vault secrets

```bash
az deployment group create \
  --resource-group <YOUR_RG> \
  --template-file keyvault-secrets.bicep \
  --parameters '@keyvault-secrets.parameters.json'
```

### Build and deploy the Container App

```bash
ACR="<YOUR_ACR_LOGIN_SERVER>"
RG="<YOUR_RESOURCE_GROUP>"

az acr build --registry $ACR --resource-group $RG \
  --image secret-governance/monitor-mcp:latest ./container-2

az acr build --registry $ACR --resource-group $RG \
  --image secret-governance/langchain-agent:latest ./container-1

az deployment group create \
  --resource-group $RG \
  --template-file deploy.bicep \
  --parameters '@deploy.parameters.json'
```

</Steps>

## UAMI permissions reference

The system uses exactly two Microsoft Graph permissions. This is intentional — no broader
permissions are needed.

| Permission | Type | Purpose |
|-----------|------|---------|
| `Application.ReadWrite.OwnedBy` | Application | Read all App Registrations (reads are unrestricted). Write — create new secrets — only on apps where UAMI is listed as owner |
| `Sites.Selected` | Application | Read/write the SecretAlertRegistry SharePoint list only — not all sites in the tenant |
| `Key Vault Secrets User` | RBAC role | Read config secrets from Key Vault |
| `Key Vault Secrets Officer` | RBAC role | Write new secret values to rotation Key Vault |
| `AcrPull` | RBAC role | Pull container images from Azure Container Registry |

<Callout type="warning">
  **Do not grant `Application.Read.All`, `Application.ReadWrite.All`, or `Sites.ReadWrite.All`.**
  These are broader than needed. `Application.ReadWrite.OwnedBy` covers everything the system
  requires — read all apps, write only owned apps.
</Callout>

## Runbook schedule

All three runbooks run on a weekly schedule in this exact order:

| Time | Runbook | What it does |
|------|---------|-------------|
| `00:00` | `runbook_discovery.py` | Scans all 255 apps, stamps `AppOwners` to SharePoint |
| `00:30` | `runbook_monitoring.py` | Triggers monitoring container — raises Jira tickets and Teams alerts |
| `01:00` | `runbook_rotation.py` | Rotates P1/P2/P3 secrets, stores new values in Key Vault |

<Callout type="info">
  The 30-minute gap between discovery and monitoring ensures SharePoint rows have correct
  `AppOwners` values before monitoring reads them.
</Callout>

| `JIRA-PROJECT-KEY` | `KAN` | Monitoring |
| `JIRA-EPIC-KEY` | `KAN-161` | Monitoring |

<Callout type="warning">
  `OWNER-EMAIL` should be set to the **display name** of your UAMI (e.g. `uami-secret-monitor`).
  The monitoring and rotation runbooks use this to filter SharePoint rows — only rows where
  `AppOwners` contains this value are actioned.
</Callout>
