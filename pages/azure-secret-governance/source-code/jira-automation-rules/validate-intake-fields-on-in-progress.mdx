# Validate intake fields on In Progress (v2)

**Rule ID:** 4071692 &middot; **UUID:** `019ffb8f-f2d5-72e5-be00-6596ca234738` &middot; **State:** Enabled

**Trigger:** `jira.issue.event.trigger:transitioned`, destination status **In Progress or
Resolved**.

<Callout type="warning">
  **Trigger widened since this rule's first review (2026-08-18).** It originally fired only on
  transition to In Progress. As of this export it also fires on transition to **Resolved**, so
  all five checks below now re-run as a final gate before a ticket can resolve, not only when
  work starts. This closes a real gap: previously, a field cleared out (or never validly filled
  in) sometime after In Progress had nothing catching it before Resolved.
</Callout>

**What it does:** five independent condition blocks, each bounces the ticket back to `To Do`
(status transition + a private, non-public comment) if triggered:

1. **Completeness gate (`ANY` match):** if `TeamName`, `ProductName`, `ProductTeamsKeyVaultName`,
   `NewSecretPresent`, `NewSecretKeyIDPresent`, or `NewSecretUpdatedReferenceInventoryPresent` is
   blank, bounce.
2. `NewSecretKeyIDPresent == Yes` but `NewSecretKeyId` is blank &rarr; bounce, "fill in the actual
   secret ID."
3. `NewSecretKeyIDPresent == Yes` and `NewSecretKeyId` is filled but fails a GUID regex
   (`^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$`) &rarr; bounce,
   "doesn't look like a valid Azure secret ID."
4. `NewSecretPresent == Yes` but `NewSecretName` is blank &rarr; bounce, "fill in the name of the
   new secret in the vault."
5. `NewSecretUpdatedReferenceInventoryPresent == Yes` but `NewSecretUpdatedReferenceInventory` is
   blank &rarr; bounce, "add the reference inventory notes."

`NewSecretKeyIDPresent`+`NewSecretKeyId` (blocks 2&ndash;3) and `NewSecretPresent`+`NewSecretName`
(block 4) are two deliberately separate Yes/No-plus-value pairs, not duplicates of each other:
"do you know the Entra Key ID" is a different question from "is a replacement secret already
stored under a given vault name," and an engineer can legitimately answer one without the other.

<Callout type="warning">
  **This rule's GUID check (block 3) does not, by itself, stop a bad value from reaching
  SharePoint.** It only gates this rule's own action &mdash; reverting the ticket's status. The
  separate [Sync field edits after In Progress](/azure-secret-governance/source-code/jira-automation-rules/sync-field-edits-after-in-progress)
  and [Sync ticket status to SharePoint](/azure-secret-governance/source-code/jira-automation-rules/sync-ticket-status-to-sharepoint)
  rules fire independently off the same events and push whatever's in `NewSecretKeyId` regardless.
  This was a real, confirmed bug: a garbage value, correctly caught by this validator, still
  landed in SharePoint. Fixed server-side in Container 2's `/tools/jira-status-update` handler
  &mdash; see [that page's Key design decisions table](/azure-secret-governance/source-code/container-2-monitor-api/container2-main).
</Callout>
