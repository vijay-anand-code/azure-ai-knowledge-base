# Sync ticket status to SharePoint

**Rule ID:** 3711027 &middot; **UUID:** `019ef2da-a7a3-7663-b9cf-8cb696bf6800` &middot; **State:** Enabled

**Trigger:** `jira.issue.event.trigger:transitioned`, destination status one of `Resolved`,
`In Progress`, `To Do`, `Waiting for Customer` &mdash; confirms these are the four real live
statuses in the KAN workflow.

**What it does:**

1. POSTs to Container 1's `/jira-status-update` proxy with `jira_key`, `to_status`, `today`, and
   the seven custom fields (`team_name`, `product_name`, `product_teams_key_vault_name`,
   `new_secret_vault_name`, `new_secret_key_id`, `new_secret_present`,
   `new_secret_updated_reference_inventory`). No `overwrite` flag &mdash; this is the blank-fill-only
   counterpart to [Sync field edits after In Progress](/azure-secret-governance/source-code/jira-automation-rules/sync-field-edits-after-in-progress)'s
   `overwrite: true` branch.
2. If `{{webResponse.status}}` does not equal `200`, POSTs a failure Adaptive Card to a
   Power Automate HTTP-trigger endpoint (relays into Teams), reporting the sync failure for that
   ticket.

<Callout type="warning">
  **The condition and the alert text use two different smart value names.** The gating condition
  (component 2 below) correctly uses `{{webResponse.status}}`, but the alert card's own text
  (component 3) was built with `{{webhookResponse.status}}` &mdash; a name Jira doesn't resolve.
  The alert still fires correctly (the condition works), but the status-code portion of its text
  likely renders blank rather than the real HTTP status. See the
  [Jira Automation](/azure-secret-governance/jira#alert-teams-if-the-web-request-fails) page for
  the corrected example.
</Callout>
